# 사진 합성을 실사처럼 만드는 법 — 연구 계획

> 작성: 2026-09-18 / 기준 커밋: `de2dbd3` (origin/main)
> 짝 문서: `photo-composite.plan.md` (기능 계획). 저건 **무엇을 만드는가**, 이건 **어떻게 좋게 만드는가** 다.
>
> 표기: **[확인]** 코드·문서 근거 있음 · **[결정]** 이 계획이 정하는 것 ·
> **[확인 필요]** 사장님만 답할 수 있는 것 · **[미확인]** 조사했지만 근거를 못 찾은 것. 지어내지 않는다.

## 0. 한 문단 요약

지금은 **방 사진 1장 + 글**만 Gemini 에 보낸다. 가구의 생김새는 전부 문장으로만 설명된다.
조사 결과 이 방식으로는 치수 정확도가 구조적으로 안 나오고, 업계 선두는 예외 없이
**기하를 먼저 확정한 뒤 생성모델을 사실감 입히기에만** 쓴다 (§2.4).

다행히 **여분 이미지를 함께 보내는 길은 워커에 이미 다 깔려 있다** (§2.2). 플래너는 이미
2048px PBR 렌더를 오프스크린으로 찍을 수 있다 (§2.3). 그래서 이 연구의 중심 가설은 하나다 —
**"가구를 글로 설명하지 말고, 3D 렌더 한 장을 같이 보내라."**

이 문서는 그 가설을 **재보고 고를 수 있게** 만드는 계획이다. 무엇을 바꿔볼지(§5),
좋아졌는지 어떻게 재는지(§4), 어떤 순서로 얼마를 써서 확인할지(§6) 를 정한다.

## 1. 지금 무엇이 문제인가 [확인]

설치 프롬프트에서 가구의 생김새를 정하는 것은 `FURNITURE:` 줄 하나다
(`workers/generate-api/src/prompts.js:578`). `design_spec` 이 있으면 도면 요약 문단으로,
없으면 품목 범용 문단으로 채워진다.

그 문단은 **글**이다. "왼쪽부터 서랍 3단, 도어 2짝, 식기세척기" 라고 적어 보내면 모델이
그림으로 옮겨 그린다. 옮기는 과정에서 개수와 순서가 흔들린다. 그걸 막을 파라미터가 없다.

### 1.1 실제로 재본 적이 없다 [확인]

더 근본적인 문제는 이것이다. **지금 이 파이프라인의 품질을 측정한 기록이 없다.**

| 없는 것 | 근거 |
|---|---|
| 생성마다 실제로 나간 프롬프트 | `generations` 표에 `prompt` 열이 없다 (`database/generations-schema.sql:18-47`) |
| 실험을 재현할 씨앗·설정 | `temperature` 는 코드 상수 (`gemini.js:71`), 행에 안 남는다 |
| QC 재시도본의 판정 | 재시도본은 QC 를 다시 안 거치고, 행의 `qc` 는 1차 판정이다 (`job.js:261-273` 재시도 · `:282` 저장) |
| 표본 방 사진 | 저장소에 없다 |

**측정 장치 없이 프롬프트를 고치는 것은 연구가 아니라 취향이다.** §7 이 먼저다.

## 2. 조사로 확정된 사실 — 연구 설계를 규정하는 제약

### 2.1 Gemini 에는 구조를 강제할 파라미터가 없다 [확인]

마스크·인페인팅 영역·ControlNet 류가 **API 스키마에 없다.** Google 이 공식 문서에서 부르는
것은 "시맨틱 마스킹" — **글로 마스크를 설명하는 것**이다.

더 중요한 사실: 구조 제어 기능은 **있다가 없어졌다.** Imagen 의 Controlled Customization
(`maskMode`, canny·scribble `controlType`, `CONTROL_SCALE`)은 **모든 Imagen 모델이
2026-08-17 종료**되면서 사라졌고, Gemini 이미지 모델에 대체 파라미터가 없다.

> 출처: [Gemini image generation](https://ai.google.dev/gemini-api/docs/image-generation) ·
> [Imagen 마이그레이션](https://firebase.google.com/docs/ai-logic/imagen-models-migration) ·
> [Nano Banana 프롬프팅 가이드](https://cloud.google.com/blog/products/ai-machine-learning/ultimate-prompting-guide-for-nano-banana)

**따라서 구조를 제어할 길은 하나뿐이다 — 구조를 입력 이미지에 그려 넣어 보내고,
프롬프트에서 그 이미지를 지목하는 것.** 파라미터로 강제하는 게 아니라 설득하는 것이다.
이 한계를 계획 전체가 전제로 깔고 간다.

서드파티 글들이 "Nano Banana Pro 가 마스크 인페인팅을 지원한다" 고 쓰는데 **공식 근거가
없다** [미확인]. 믿고 설계하지 않는다.

### 2.2 여분 이미지를 보내는 길은 **이미 다 깔려 있다** [확인]

이게 이번 조사에서 가장 값진 발견이다. 새로 만들 배관이 없다.

| 구간 | 상태 | 근거 |
|---|---|---|
| 요청 본문 `reference_images` | 받는다 — `{base64, mimeType, role}`, **최대 5장** | `worker.js:234`, `MAX_REFS` `:52` |
| 역할 구분 | `role: 'theme'` / 그 외는 전부 `'style'` | `normalizeRefs` `worker.js:95-112` |
| 버킷 저장 | `{user}/{gen}/ref-N.{ext}` → `inputs.refs` | `worker.js:305-322` |
| Gemini 설치 호출 | `images: [room, ...refs]` — **방 사진 다음에 그대로 실린다** | `job.js:243-251`, 설치 `:247` · QC 재시도 `:266` |
| 클라이언트 선례 | `ai-design.html:1144` 가 이미 쓴다 | — |

**그런데 프롬프트가 정반대를 지시하고 있다** [확인]. 지금 ref 가 붙으면 이 문장이 나간다
(`prompts.js:554-558`):

> "The additional images are style reference: match the door colour, material grain direction,
> sheen and overall mood of the reference fronts. **Never copy the reference layout, room or camera.**"

도면 렌더를 지금의 `role:'style'` 로 보내면 **모델에게 그 배치를 베끼지 말라고 명시적으로
말하는 셈이다.** 그래서 이 연구의 첫 실험은 "렌더를 보낸다" 가 아니라
**"렌더용 역할과 문장을 새로 만든다"** 여야 한다.

### 2.3 플래너는 이미 잘 찍는다 [확인]

`js/planner/planner-capture.js` 가 화면을 건드리지 않고 오프스크린으로 찍는다.

- 뷰 4종: `front`(FOV 12°, 직교 근사) · `iso` · `plan` · `module:<id>` (`:229-274`)
- 긴 변 **2048 기본 / 4096 고해상**, MSAA 4× + `OutputPass` 톤매핑 + sRGB (`:50-51`, `:477-491`)
- 디테일 룩을 캡처 한 장 동안만 켠다 — `pushLook()/popLook()` (`:453`, `:511`)
- 재질: `MeshPhysicalMaterial`, tone 별 PBR, **예림 타일 144종 실제 텍스처** (`planner-materials.js:156-201`)
- 카메라 파라미터를 `design_renders.camera` JSONB 로 이미 보존한다 (`database/design-renders.sql`)

**작은 코드 추가가 필요한 것** (전부 변경 지점이 좁다):

| 필요 | 지금 | 고칠 곳 |
|---|---|---|
| 투명 배경 | 알파를 255 로 덮어쓴다 | `planner-capture.js:343` 한 줄 조건화 + `scene.background` 임시 null |
| 가구만 (그리드·바닥·마커 제거) | 씬 전체를 그린다 | 캡처 전후 `visible` 토글 |
| 임의 카메라 | 프리셋 4종만 | `capturePixels(opt.frame)` — `plannerCaptureFrame` 이 순수 함수라 걸림돌 없음 |

### 2.4 경쟁사는 전부 기하를 먼저 만든다 [확인]

### 2.5 사진 1장에서 **각도**는 나오지만 **절대 치수**는 안 나온다 [확인]

- 카메라 각도·화각 추정은 실용 수준이다 (GeoCalib, Perspective Fields, AnyCalib).
- **절대 스케일은 아니다.** 단일 사진 메트릭 뎁스 실내 오차: Metric3D v2 AbsRel 4.5%,
  Depth Pro 15.6%, 실측 MAE 0.41 m.
- 3000mm 벽에 5% 만 실려도 **±150mm**. 붙박이장 한 칸이 통째로 틀어지는 크기다.
- 업계 정리: "fully automatic scale from monocular images remains unreliable."

**문틀 900×2100 기준자의 한계** [확인]: 한국 현관문은 900 과 1000 이 병존하고, 문틀 외곽·
개구부·문짝 중 무엇을 재느냐로 40~60mm 가 갈린다. 문이 **다른 벽**에 있으면 원근 때문에
거의 무효다. 지금 `buildAnalysisPrompt` 는 이 값을 유일한 기준자로 쓰고 있다
(`prompts.js:106`). **보조 신호로 강등해야 한다.**

> 출처: [Metric3D v2](https://arxiv.org/pdf/2404.15506) · [Depth Pro](https://arxiv.org/pdf/2410.02073) ·
> [단안 메트릭 뎁스 서베이](https://arxiv.org/pdf/2501.11841) · [GeoCalib](https://arxiv.org/pdf/2409.06704) ·
> [가상 스테이징 한계](https://virtualstaging.com/blog/when-not-to-use-virtual-staging-ai/)

### 2.6 입력 이미지는 **공짜에 가깝다** [확인]

| 항목 | 값 |
|---|---|
| `gemini-3-pro-image` 2K 출력 | **$0.134 / 장** |
| 입력 이미지 1장 | 약 560 토큰 ≈ **$0.0011** |
| `gemini-3-pro-image` 고충실도 물체 슬롯 | **6장** |
| `gemini-3.1-flash-image` 물체 슬롯 | 10장 (+스타일 3) |

**레퍼런스를 6장 넣어도 1센트가 안 된다.** 입력 이미지를 아끼는 설계를 할 이유가 전혀 없다.
반대로 우리 `MAX_REFS = 5` 가 모델 한계보다 낮다.

> 출처: [Gemini API 가격](https://ai.google.dev/gemini-api/docs/pricing) ·
> [모델별 입력 한도](https://ai.google.dev/gemini-api/docs/image-generation)

### 2.7 여러 장을 줄 때의 공식 권장법 [확인]

역할을 지정하는 **API 필드가 없다.** Google 이 권하는 것은 두 가지다.

1. **각 이미지에 이름을 붙이고 프롬프트에서 그 이름으로 지시한다** — DeepMind 가이드:
   "assign a distinct name to each character or object in your prompt."
2. 문장 공식: `[레퍼런스 설명] + [관계 지시] + [새 장면]`

지금 우리 프롬프트는 "the additional images" 라고 뭉뚱그린다. **이름을 주는 것만으로도
실험 가치가 있다.**

목표는 **"내 설계처럼 보이는 사진"** 이지 제작 도면이 아니다 (`photo-composite.plan.md` §4.1-5).

## 4. 어떻게 재는가 — 이 계획의 핵심

### 4.1 자동 채점: **역판독이 이미 있다** [확인]

`workers/generate-api/src/layout.js` 는 **완성된 이미지를 Claude 비전에 보여 구성을 읽어낸다.**
좌→우 세그먼트 순서, 종류, 시작·끝 %, 도어 수, 서랍 수, 가전 위치.

그 출력 모양이 **우리가 보낸 `design_spec` 과 같은 종류다.** 그러므로:

```
design_spec (보낸 도면)  →  [생성]  →  이미지  →  [layout.js 역판독]  →  읽힌 구성
                                  └──────────── 대조 ────────────┘
```

**닫힌 고리가 공짜로 완성된다.** 새 채점 모델을 만들 필요가 없다.

| 점수 | 정의 | 만점 |
|---|---|---|
| `S_count` | 구간별 모듈 개수가 맞나 | 1.0 |
| `S_order` | 좌→우 종류 순서가 맞나 (편집거리) | 1.0 |
| `S_doors` | 도어·서랍 개수 합이 맞나 | 1.0 |
| `S_appl` | 가전 종류와 좌→우 순서가 맞나 | 1.0 |
| `S_pos` | 가전 위치 % 오차 (±10%p 안이면 만점) | 1.0 |

**합계 `S_layout` = 5점 만점.** [결정]

주의 [확인]: `layout.js` 는 **mm 를 읽지 않는다** — "렌더는 프롬프트로 그린 그림이라 원근·
크롭이 있다" 는 이유로 일부러 뺐다 (`layout.js:7-13`). 그 규율을 채점에서도 지킨다.
**우리도 mm 를 채점하지 않는다. 순서와 개수만 잰다.**

### 4.2 방 보존 점수 [결정]

RQ5 용. 텍스트 모델에 **원본 사진과 결과 두 장**을 주고 묻는다 (지금 QC 는 결과 한 장만 본다).

| 항목 | 질문 |
|---|---|
| `P_camera` | 시점·화각이 같은가 |
| `P_room` | 벽·천장·바닥·창·문이 그대로인가 |
| `P_light` | 빛의 방향과 색이 그대로인가 |
| `P_outside` | 가구 밖 영역에 없던 것이 생기지 않았나 |

각 0/0.5/1 → **`S_room` = 4점 만점.**

### 4.3 사람 평가 — 쌍 비교 [결정]

자동 점수는 "도면에 충실한가" 만 잰다. **"진짜 사진 같은가" 는 사람만 답할 수 있다.**

- 같은 사진·같은 도면으로 만든 두 결과를 **나란히 놓고 좌우를 무작위로 섞어** 고르게 한다.
- 물음은 하나: **"둘 중 어느 쪽을 고객에게 보여주겠습니까?"**
- 평가자: 사장님 + 현장 [확인 필요 — 몇 분이 봐 주실 수 있는지]
- 최소 표본: 조합당 **10쌍**. 7대3 이상 갈리면 차이로 본다. [결정]

**자동 점수가 높은데 사람이 안 고르면 사람을 따른다.** 자동 점수는 후보를 좁히는 체이지
판결이 아니다.

## 6. 순서와 비용

**원칙**: 싼 것부터, 그리고 **한 번에 한 축만** 움직인다. [결정]

| # | 실험 | 축 | 실행 수 | 무엇을 답하나 |
|---|---|---|---|---|
| **E0** | 계측 장치 (§7) | — | 0 | 재현·감사 가능하게 |

| **E2** | 렌더 투입 — A1 vs A2(B1) + C2 | A·C | 18 | **중심 가설** |
| **E3** | 렌더 모양 — B1 vs B2 vs B3 | B | 18×2 = 36 | 어떤 렌더가 좋은가 |
| **E4** | 프롬프트 — C2 vs C3 vs C4 | C | 18×2 = 36 | 문장으로 얼마나 더 가나 |

추천안 3장은 **끄고 돈다** — 리컬러일 뿐이라 이 연구와 무관하고 비용이 4배가 된다 [결정].

| 항목 | 값 |
|---|---|
| 실행 1회 이미지 값 | 약 **$0.134** (2K) |

## 7. 먼저 만들어야 하는 것 — 계측 장치 (E0)

이게 없으면 나머지가 다 무의미하다. **연구의 첫 PR 이다.**

1. **프롬프트·설정 기록** — `generations` 에 `prompt_text`, `temperature`, `model`,
   `experiment_arm` 을 남긴다. 어느 실험의 몇 번 실행인지 나중에 되짚을 수 있어야 한다.
   [확인 필요 — 고객 생성분에도 남길지, 연구 플래그가 있을 때만 남길지]
2. **추천안 끄기** — 요청에 `variants: false` (이름은 구현 PR 이 정한다). 비용 4배 절감.
3. **역판독 자동 실행** — 지금은 별도 라우트를 사람이 불러야 한다 (`worker.js:177` 의 `/layout` 하위 경로).
   연구 실행에서는 끝나고 바로 돌려 `layout` 을 채운다.
4. **연구 실행 경로** — 크레딧을 안 태우는 길. 가장 단순한 안은 **연구 계정에 크레딧을
   충분히 넣고 그대로 쓰는 것** [결정 — 새 우회로를 만들지 않는다. 우회로는 곧 구멍이 된다].
5. **채점기** — `S_layout`(§4.1)·`S_room`(§4.2) 을 계산하는 스크립트. 순수 함수로 두고
   시험을 붙인다 (`test-utils/` 관례).
6. **결과 대조판** — 같은 조합의 여러 안을 나란히 놓고 좌우를 섞어 보여주는 한 페이지.
   §4.3 의 쌍 비교를 사람이 실제로 할 수 있게.

## 10. 위험

1. **방이 조용히 바뀐다** [확인]. 편집은 전체 재생성이라 몰딩·창틀·바닥 무늬가 미세하게
   달라질 수 있고, 모델이 "개선" 하려 든다 (없던 조명·새 바닥). `S_room` 으로 재고,
   3.0 미만이면 채택하지 않는다.
2. **고지 의무** [확인]. 캘리포니아 AB 723 이 2026-01-01 시행돼, 부동산 이미지에 실물을
   바꾸는 편집을 하면 고지와 원본 접근 제공이 의무다. 가구 판매는 중개가 아니지만
   "고객 집 사진을 AI 로 바꿔 보여준다" 는 같은 문제군이다. **한국 규제는 [미확인].**
   → **결과 이미지에 "AI 합성 이미지 · 실제 시공과 다를 수 있습니다" 를 붙인다** [결정].
   이건 연구 결과와 무관하게 지금 해야 한다.
3. **특허** [확인·부분]. US 12475666 이 "가구 형상 레퍼런스 이미지로 diffusion inpainting 을
   ControlNet 으로 유도" 하는 파이프라인을 다룬다. 양수인은 판독 실패 [미확인].
   §9 의 ControlNet 경로를 열게 되면 **청구항을 먼저 법무 검토**한다.
4. **모델 이름** [미확인]. `wrangler.toml` 의 `gemini-3.8-flash` 를 Google 공식 모델 목록에서
   확인하지 못했다. 공식 목록은 `gemini-3-pro-image`, `gemini-3.1-flash-image`,
   `gemini-3.1-flash-lite-image`, `gemini-2.5-flash-image`(레거시) 다. **E0 에서 실제 호출로
   확인한다** — 텍스트 모델이 조용히 폴백되고 있다면 분석·QC 품질에 직접 영향이 있다.
5. **분석 실패가 조용하다** [확인]. 분석이 실패하면 3000×2400 기본값으로 계속 가고,
   그때 `site`·`tile` 키가 없어 SITE·WALL TILE 문단이 통째로 빠진다
   (`job.js:195-202` — 기본값 객체에 `site`·`siteNotes`·`tile` 키가 없다. vs `prompts.js:126-128`). 연구 실행에서 이게 섞이면 결과가 오염된다.
   **E0 에서 분석 실패를 실행 기록에 남기고, 실패한 실행은 표본에서 뺀다.**
