# 자동계산 규칙 정본 — 강화학습 전환 대비 보관본

> **왜 따로 두는가.**
> 자동계산은 앞으로 강화학습 기반으로 대체된다. 그때 지금의 함수들은 사라지거나
> 학습 모델의 뒤로 밀려나는데, **규칙 자체는 사라지면 안 된다.** 세 가지 역할이 남는다:
>
> 1. **학습 목표** — 모델이 무엇을 잘해야 하는지의 정의
> 2. **폴백** — 모델이 답을 못 내거나 신뢰도가 낮을 때 돌아갈 자리
> 3. **검증 기준** — 모델 출력이 제조 가능한지 판정하는 선
>
> 그래서 "코드가 이렇게 되어 있다"가 아니라 **"규칙이 무엇인가"**로 적는다.
> 모든 항목에 근거 위치를 병기한다. 추출 시점 2026-08-16 / 기준 커밋 `6a3df64`.

## 2. 도어 분배 — `distributeModules(totalSpace)`

`js/planner/planner-engine.js:100`. TS 원본은 `planner-vite/src/lib/calc-utils.ts`.

**목표**: 주어진 폭을 도어 몇 장으로, 각 몇 mm 로 나눌지 정한다.

### 절차

1. 도어 수 후보 범위를 잡는다.
   `minCount = ceil(폭 / 600)`, `maxCount = min(floor(폭 / 350), max(round(폭/450) + 3, minCount + 5))`
2. 각 후보 수마다 **폭 후보 3가지**를 만든다.
   - 균등 — `floor(폭 / n)`
   - 10단위 내림 — `floor(폭 / n / 10) * 10`
   - 짝수 내림 — `floor(폭 / n / 2) * 2`
3. 각 후보는 **두 관문**을 통과해야 살아남는다.
   - 도어 폭이 350 ≤ w ≤ 600
   - 잔여(gap)가 0 이상 **10 이하**
4. 살아남은 후보를 이 순서로 정렬해 첫째를 택한다.
   **① 450 에 가까운 순 → ② 잔여 작은 순 → ③ 도어 수 적은 순**
5. 후보가 하나도 없으면 폴백: `calcDoorCount(폭)` 으로 수를 정하고 균등 분할 (잔여 허용).
6. **양문 페어링** — 도어 `n` 장 중 `floor(n/2)` 쌍을 폭 `2w` 짜리 셀 하나로 묶고(`is2D`),
   홀수면 남은 1장을 단문 셀로 둔다.
7. 잔여 gap 은 셀에 균등 분배하고 **끝 셀이 나머지를 흡수**한다.

### 폴백 도어 수 — `calcDoorCount(W)`

`planner-engine.js:88`. 구간 고정값이며 위 알고리즘이 실패했을 때만 쓰인다.

| 폭 | ≤600 | ≤1000 | ≤1400 | ≤1800 | ≤2200 | 초과 |
|---|---|---|---|---|---|---|
| 도어 | 1 | 2 | 3 | 4 | 5 | `round(W / 450)` |

## 3. 선반 — `calcDefaultShelves(section, H)`

`js/planner/planner-engine.js:150` 부근.

**규칙**: 선반 간격이 `MIN ≤ 간격 ≤ MAX` 를 만족하는 범위에서 **선반 수를 최대로** 잡는다.
간격은 `H / (선반수 + 1)` 로 균등하다.

1. `count = floor(H / MIN) − 1` (간격 ≥ MIN 을 만족하는 최대 수)
2. `count ≤ 0` 이면 선반 없음
3. `간격 > MAX` 면 `count = ceil(H / MAX) − 1` 로 늘려 상한도 만족시킨다
4. 위치는 바닥부터 `round(간격 × i)`

여기서 `H` 는 **몸통 높이**다(다리발·상몰딩 제외).

> ⚠ **상판(topT)은 빼지 않는다.** `autoCalcModule` 은 `H − 다리발 − 상몰딩` 을 쓴다.
> 높이 패널의 `bodyHeightOf` 는 상판까지 빼므로 **두 값이 상판 두께만큼 다르다.**
> 하부장 850 기준 — 엔진 700 / 높이 패널 688. 미해결 항목이다.

## 8. 전체높이 모델 (플래너 밖 정본)

`js/detaildesign/data-constants.js:43`. 자동계산의 입력이자 BOM 의 기준.

```
하부장 870 = 다리발 150 + 몸통 708 + 상판 12
상부장 780 = 몸통 720 + 상몰딩 60
```

**플래너 도면의 사각형 높이는 전체 높이다. 몸통이 아니다.**

변환을 빠뜨리면 하부 +162mm(= 150 + 12), 상부 +60mm 로 전 부재가 크게 재단된다.

## 9. 목찬넬 따내기 (W12-5)

하부장 손잡이가 **목찬넬**이면 측판·칸막이의 **상단 전면 모서리를 70(H) × 40(D) 따낸다.**
따낸 자리는 ㄴ자로 채운다.

```
측판 옆면 · 오른쪽이 정면          따낸 자리 단면

  ┌─────────────┐                    ┌────┐ ─┬─
  │             │                    │    │  │ 전면판 52 × 18T
  │             └──────┐  ─┬─        │    │  │
  │                    │   │ 70     ┌┴────┴┐─┴─
  │                    │  ─┴─       │ 지면판 40 × 18T │
  └────────────────────┘            └───────────────┘
                ├─ 40 ─┤             18 + 52 = 70
```

| 값 | 출처 |
|---|---|
| 전면판 52 × 18T | `design_rules` 목찬넬전면 · `sink.md` EP 부재표 |
| 지면판 40 × 18T | `design_rules` 목찬넬지면 · `sink.md` EP 부재표 |
| 따내기 70 | 18 + 52. `sink.md` 의 `bandH = H-36-70` 과 같은 70 |
| 따내기 40 | 지면판 폭 |

- **전면판은 따낸 자리 안쪽(뒤)에 선다.** 앞쪽 `40 − 18 = 22mm` 가 손 넣을 자리다.
  도어 H 가 `장H − 30` 이라 도어 위에 30mm 틈이 생기는데, 전면판을 맨 앞에 세우면
  그 틈을 막아 손잡이 구실을 못 한다.
- **칸막이도 같이 따낸다.** 지면판이 설치공간 전폭(`effectiveW`)에 걸쳐 있어
  칸막이를 통짜로 두면 판이 뚫고 지나간다.
- **천판은 따낸 깊이만큼 뒤로 물린다.** 안 그러면 전면판과 같은 칸을 차지한다.
- 상수: `MASTER_RULES.CHANNEL_NOTCH_H/D`, `CHANNEL_BOARD_T`, `CHANNEL_FRONT_W`, `CHANNEL_BACK_W`
- 상부장 목찬넬은 **아직 규칙이 없다** — 상부장은 도어 내림(아래 §9.1)을 쓴다.
  `isWoodChannel()` 이 하부장 단으로 제한하는 이유다.

### 9.1 단별 기본 손잡이 (W12-6 / W12-7)

| 단 | 기본 | 표현 |
|---|---|---|
| 하부장 (독립·스택 단) | 목찬넬 | 따내기 70×40 + ㄴ자 부재 (§9), 도어 = 장H − 30 |
| 스택 중간장 | 푸쉬 | 부재 없음 |
| 스택 상부장 (키큰장·냉장고장) | 푸쉬 | 부재 없음 |
| 독립 싱크 상부장 | **도어 내림** | 도어 = 장H + 15, 몸통 아래로 15 내려옴 |
| (선택) | 알루미늄 찬넬 | 52×12 매립 막대 — 직접 고를 때만 |
| (선택) | C찬넬 | 3D 표현 없음 |

- **스택의 중간장·상부장은 전부 푸쉬다** (W12-10). 단 이름(`m.part`)으로 가르므로
  키큰장·냉장고장을 구분하지 않는다. 하부장 단만 아래로 빠져 목찬넬이 된다.
- **푸쉬를 도어 내림보다 먼저 걸러야 한다** — 순서가 뒤바뀌면 스택 상부장이
  도어 내림으로 잡힌다. 테스트가 순서를 지킨다.
- 도어 내림은 **독립 싱크 상부장**에만 남는다.

- **도어 내림 15mm** — `design_rules` 싱크상부장도어H. 2026-08-27 에 20 → 15 로
  바꾸고 방향을 "상몰딩 안쪽까지"에서 "몸통 아래로"로 확정했다. `sink.md` 상부장
  부재표의 도어 세로도 `H+15` 로 같이 고쳤다.
- **목찬넬 도어는 장H − 30** (W12-8) — 도어 상단이 몸통 상단보다 30 내려오고
  밑단은 다리발 위(몸통 바닥)에 맞는다. **그 30mm 가 손 넣는 자리다.**
  정본은 `design_rules` 싱크하부장도어H · `sink.md` 하부장 부재표 `(H-30)` ·
  `SINK_LOWER_DOOR_H_MINUS` 셋이 일치했지만 **플래너만 갭 4 로 그려** 상단 틈이
  2mm 였다 — 도어가 목찬넬을 덮어 손잡이가 없는 것과 같았다.
  푸쉬·알루미늄 찬넬 하부장에는 적용하지 않는다 (그 손잡이엔 없는 틈이다).
- 도어를 그릴 때 넘어오는 높이는 **갭 4 를 이미 뺀 값**이다. 그냥 더하면 장H + 11 이
  되므로 갭을 되돌린 뒤 더해야 장H + 15 가 나온다.
- **`'channel'` 은 고른 값이 아니다.** 예전 기본값이라 모든 모듈에 알루미늄 막대가
  붙어 있었다. `'auto'` 와 함께 기본형으로 읽고, 직접 고르면 `'alu-channel'` 로 저장한다.
- **푸쉬 금지는 이미지 생성 한정이다.** `ACTIVE_RULES.md` §15 의 금지 목록은 프롬프트
  규칙이고, 제조(플래너)에서는 푸쉬를 고를 수 있다.

### 9.2 모듈 마감재 (W12-11)

모듈을 클릭 → 팔레트 **마감** → 좌·우에 EP·몰딩·휠라를 붙인다.

- **영역 폭은 그대로 두고 모듈이 줄어든다.** 마감재가 가져간 폭을 모듈에서 빼지
  않으면 마지막 모듈이 영역 밖으로 나간다. 영역 안 총 폭이 불변식이다.
- 좌측이면 모듈이 오른쪽으로 물러나고 마감재가 원래 왼쪽 끝을 쓴다.
  우측이면 모듈 자리는 그대로고 줄어든 끝에 선다. **양쪽 다 바깥 끝은 안 움직인다.**
- 같은 쪽을 바꿔 달 때는 **먼저 떼고(폭 복원) 붙인다** — 안 하면 바꿀 때마다
  모듈이 조금씩 좁아진다.
- 모듈이 `DOOR_W_MIN`(350) 보다 좁아지면 붙이지 않는다.
- 호스트를 지우면 붙어 있던 마감재도 같이 지운다. **자동계산은** 마감재를 보존하되
  `hostId` 를 끊어 **영역 마감재로 승격**한다 (사람이 놓은 것을 없애지 않는다).
- **EP 는 부재와 공간이 다른 값이다** (W12-19).
  | | 값 | 쓰는 곳 |
  |---|---|---|
  | 부재 두께 | **18T** | BOM · 3D·정면도에 그리는 판 (`finishingPartWidthOf`) |
  | 공간 폭 | **20mm** | 모듈 폭을 줄이는 값 · 영역 잔여 계산 (`finishingWidthOf`) |

  차이 2mm 는 **실제 설치 여유**다. `design_rules 'EP기본값' 20mm` 과 `door.md`
  FINISH_TYPES '기본 너비 20mm' 가 공간값이고, `sink.md` 의 18T MDF 가 부재값이다.
  W12-12 에서 둘을 같은 것으로 보고 18→20 으로 바꿨다가, W12-18 에서 18 로 되돌렸다가,
  W12-19 에서 **둘 다 필요하다**는 것을 알고 나눴다.
  몰딩·휠라는 폭 60 이 부재이자 공간이라 둘이 같다.
- **마감재 치수는 배치 공간(영역) 기준이다** (W12-18). 냉장고장 영역 H2300 · D700 이면
  EP 는 `2300 × 700 × 18T`. 호스트 모듈 치수를 쓰면 스택의 한 단(상부장 400)만큼만
  서서 반토막이 난다.
- **배치 팔레트는 늘 네 항목이다** (W12-18) — 크기 · 좌대 · 상몰딩 · 마감.
  그 섹션의 높이 모델에 없는 부위는 **숨기지 않고 입력을 막고** 무엇을 대신 쓰는지
  적는다. 숨기면 영역마다 개수가 2~4개로 달라져 무엇이 빠졌는지 알 수 없다.
- **배치 팔레트의 마감은 영역 끝 한 장씩이다** (W12-20). 모듈마다 붙이면 나란한
  모듈 사이에 마감재 두 장이 맞닿아 실제 제작과 다르다. 폭은 그 끝의 **바깥쪽 모듈**이
  내놓고, 영역 안 총 폭은 그대로다. 모듈 팔레트의 개별·일괄은 그대로 남는다.
- **스택 영역(키큰장·냉장고장)은 모든 단이 함께 폭을 내놓는다** (W12-22).
  스택은 3단이 같은 x·같은 W 로 쌓이므로 좌우 끝을 x 로 고를 수 없다. 한 단만
  줄이면 나머지가 마감재를 뚫고 나온다 (하부장만 880, 중간장·상부장은 900 이었다).
  마감재는 영역에 매인다(`hostAreaId`) — 모듈에 매이는 가로 배치와 다르다.
  자동계산도 이미 놓인 마감재 폭을 빼고 그 옆에서 단을 만든다.
- **마감 입구는 배치 팔레트 하나다** (W12-21). 모듈 팔레트의 마감 옵션과
  일괄 적용(W12-11/14)은 없앴다 — 모듈마다 붙이면 나란한 모듈 사이에 마감재
  두 장이 맞닿는다. `setModuleFinish` 는 엔진으로 남아 `setAreaFinish` 가 부른다.
- **마감재는 판 한 장으로 그린다** (W12-13). 3D·정면도 모두 캐비넷 경로를 타기 전에
  갈라진다. 예전엔 마감재도 일반 모듈로 그려져 폭 20~60mm 에 측판을 18mm 씩 두 장
  세웠고, 지판·천판 폭이 **음수**가 됐다 (EP 에서 -16). 도어·상판·다리발까지 붙었다.
  판은 모듈 전체 H·D 를 그대로 쓴다 — 옆 모듈에 맞춰 서는 것이 마감재의 뜻이다.
  EP 는 `design_rules` 'EP기본값' 과 `door.md` FINISH_TYPES 가 둘 다 20 인데
  코드만 18 이었다 (W12-12 에서 맞췄다). 단일 소스는 `planner-sections.js` 의 `ep.h`.

### 9.3 배치 공간은 제한 공간이다 (W12-24)

모듈·도어·마감재 **무엇도 영역 밖으로 나가지 못한다.** 실측으로 셋이 나가 있었다:

| 나간 것 | 크기 | 원인 |
|---|---|---|
| 상부장 마감재 | `Y-1520` | 상부장은 천장 매달림인데 마감재 section('ep')이 바닥 기준으로 섰다 |
| 도어 | `Z+18` | overlay 라 몸통 앞면에 붙는데 영역 깊이가 몸통과 같았다 |
| 상부장 도어 | `Y-15` | 도어 내림이 영역 아래를 넘었다 |

- 마감재는 **영역 섹션**으로 baseY 를 구한다 (`finishBaseYFor`). 마감재 자신의
  섹션으로 구하면 상부장 영역에서 1520mm 아래에 서서 "안 생긴다"로 보인다.
- 도어는 `areaLimitsFor(m)` 가 준 `frontLimit`·`bottomLimit` 에서 멈춘다.
  영역이 몸통보다 깊으면 제한이 걸리지 않아 예전 그대로 몸통 앞에 붙는다.

> **남은 것**: 90° 회전 영역은 **모듈 자체**가 영역 밖으로 나간다(실측 28건,
> `back`·`left` 까지). 도어 문제가 아니라 회전 영역의 모듈 배치 문제이고
> W12-24 이전부터 있었다. §10 에 올린다.

### 9.4 파츠는 서로 겹칠 수 없다 (W12-25)

- **몸통 두께는 15T** — `data-constants.js` 의 `BODY_THICKNESS_DEFAULT` 가 정본이고
  현장 기준 15T 90% / 18T 가끔이다. 플래너는 네 곳에서 `T = 18` 을 박아 쓰고 있었다.
  도어·마감재의 18T 는 **몸통과 무관한 별개 값**이라 그대로다 (`DOOR_T`).
- **뒤판은 측판 사이에 들어간다** (`W − 2T`). 전폭으로 두면 측판과 두께만큼 겹친다.
- **배치 공간 깊이 = 몸통 + 도어.** 몸통을 영역 깊이 그대로 잡으면 도어가 영역 밖으로
  나가거나(W12-24 전) 몸통 속으로 파고든다(W12-24 후). 새 모듈의 깊이를
  `영역 D − 도어 두께` 로 잡아야 둘 다 안 생긴다.

**천판은 몸통 상단에서 끝난다** (W12-40). 예전엔 `H − 상몰딩` 으로 잡아 **상판
두께만큼 위로 떠 있었다** — 측판은 몸통 상단(858)에서 끝나는데 천판만 870 까지
올라가 상판(858~870)과 12mm 겹쳤다. §9.11 로 상판 기본값이 12 가 되면서 모든
하부장에 드러났다. 목찬넬 자리를 잡는 `addWoodChannel` 은 처음부터
`legH + carcassH` 를 쓰고 있었다.

> 실측: 전체 쌍 겹침 19건 → **16건**. 사라진 3건이 상판↔천판이다.

> 겹침 검사에서 **목찬넬 ↔ 측판 4건은 과검출**이다. 따낸 판(L자)의 `Box3` 는
> 외접 사각형이라 도려낸 자리도 포함한다. 좌표로 확인하면 목찬넬은 따낸 자리
> 안에 정확히 들어간다.

### 9.5 편집 지점은 우측 패널 하나 (W12-28 ~ W12-31)

같은 값을 고치는 자리가 **두 곳**이었다 — 떠 있는 팔레트(`.mod-palette`)와
우측 패널(`#rightPanel`). 둘이 같은 구조 객체를 고치는데 저장과 동기화가
한쪽으로만 흘러, 우측 패널에서 바꾼 분할·도어·선반·손잡이는 **저장되지 않았다**.
팔레트가 저장을 대신해 드러나지 않았을 뿐이다.

| 단계 | 고친 것 |
|---|---|
| W12-28 | `persistPlannerState` 가 `saveLayoutFromModules` 뒤에 `saveStructModules` 를 다시 찍는다 (`savedAt` 도장 어긋남) |
| W12-29 | 우측 패널의 모든 입력이 `panelCommit()` 을 지난다 — 저장 + 정면도·3D 재렌더 |
| W12-30 | 정면도 칸 클릭으로 도어 방향. 팬의 `setPointerCapture` 가 **정면도의 모든 클릭을 삼키고 있었다** — 4px 넘게 움직인 뒤에만 캡처한다 |
| W12-31 | 우측 패널이 **모듈 모드 / 영역 모드** 두 가지. 팔레트에만 있던 크기 W/H/D·고정을 옮겼다 |
| W12-32 | 팔레트 제거. 편집 지점이 우측 패널 **하나**가 됐다 (−588줄) |

**우측 패널의 두 모드** — 섹션 마크업은 한 벌이고 `PANEL_LAYOUT` 이 무엇을 보일지만 정한다.

| 모드 | 섹션 |
|---|---|
| 모듈 | 크기·고정 · 높이 구성 · 분할 · 영역 타입 + 도어 열림 · 선반 · 손잡이 |
| 영역 | 영역 크기 · 높이 구성(좌대·상몰딩) · 마감 |

모드는 `activeId`/`activeAreaId` 로 가르지 않는다 — 둘은 서로를 지우지 않는다.
**마지막으로 고른 것**(`panelTarget`)을 따른다.

**한 곳으로 모은 규칙 넷** (팔레트와 우측 패널이 같은 함수를 부른다):

| 함수 | 규칙 |
|---|---|
| `applyModuleDim` | 폭이 바뀌면 `areaWidths`·`areaIs2D` 를 비운다. 높이를 줄이면 몸통 밖 선반을 지운다 |
| `applyHeightPart` | 몸통이 50mm 미만이 되면 **되돌린다**. `delete` 가 아니라 이전 값을 되놓는다 |
| `areaPartInfo` | 그 섹션에 없는 부위는 숨기지 않고 **막고 무엇을 쓰는지 적는다** (§9.2 의 항목 수 통일) |
| `syncFinishingsToAreas` | 영역 크기를 고치면 마감재 H·D 가 따라온다 |

> 마지막 것이 실제 결함이었다. 마감재는 만들 때 영역 H·D 를 받아 가는데(§9.2),
> 그 뒤 영역을 2300→2100 으로 줄여도 EP 는 2300 인 채로 남았다.

**팔레트가 가져간 것** (W12-32) — 지우면서 갈 곳을 정한 항목들:

| 팔레트 항목 | 어디로 |
|---|---|
| 크기 W/H/D · 고정 | 우측 패널 **크기** 섹션 |
| 다리발·상판·좌대·상몰딩 | **높이 구성** (이미 있던 자리) |
| 구성·서랍 단수·도어 갯수 | **분할** (`#inpVCount` 가 같은 값이었다) |
| 도어 열림 방향 | **정면도 칸 클릭** (W12-30) |
| 선반 갯수 | **균등 재배치 버튼** — 개별 위치를 통째로 날리므로 숫자 입력이 아니라 버튼이다 |
| 손잡이 | **손잡이** (이미 있던 자리) |
| 영역 크기·좌대·상몰딩·마감 | 우측 패널 **영역 모드** |
| ⚡ 이 모듈 계산 | 없앴다 — 이름과 달리 세트 전체를 계산했다. 영역 도구의 `이 영역 자동계산` 이 맞는 것이다 |

> `test-marker-guard` 가 없었다면 마커가 사라진 슬라이스 테스트들이
> 빈 문자열을 검사하며 **조용히 통과**했을 것이다 — 실제로 16건이 걸렸다.

### 9.6 모듈은 앞쪽에 앉되 물끊기만큼 물러난다 (W12-33 → W12-54 개정)

배치 공간 깊이는 곧 **상판 깊이**다 (§9.4). 앞선에서부터 이렇게 나뉜다:

```
배치 공간 깊이 = 물끊기 10 + 도어 자리 20 + 몸통 깊이 + 여유(뒤)
         700  =        10 +          20 +      550 +      120
```

여유공간은 입력이 아니라 **남는 값**이다. 조립체는 앞쪽에 붙되 앞선에서
물끊기 자리만큼 물러나고, 남는 깊이는 뒤에 둔다 — 뒤는 배관이 지나간다.

```
몸통 앞면 = m.y + m.D = area.y + area.D − 30
도어 앞면 = 몸통 앞면 + DOOR_T(18) = 앞선 − 12   → 물끊기 ≥ 10
```

| 영역 D | 모듈 D | 뒤 여백 | 몸통 | 도어 | 물끊기 |
|---|---|---|---|---|---|
| 700 | 550 | **120** | 120–670 | 670–688 | 688–700 |

> 도어 **자재는 18T** 그대로다 (`DOOR_T`). 20 은 시공 갭을 포함한 **자리**값이라
> 발주 치수가 아니다 (`DOOR_SEAT_D`). 그 2mm 차이는 물끊기를 12 로 넉넉하게
> 만들 뿐이고, 규칙의 최소 10 은 언제나 지켜진다.

**W12-33 은 도어 앞면을 앞선에 딱 붙였다.** 그러면 상판 끝과 도어가 같은 면이
되어 **물끊기가 사라진다** — 상판에서 떨어진 물이 그대로 도어를 탄다.
그보다 더 예전에는 `m.y = area.y` 라 모듈이 뒤에 붙고 **앞이 통째로 비었다**
(위 예에서 132mm). 세 번째가 맞다: 앞쪽에 붙이되 물끊기를 남긴다.

> 골든 3종이 이 변경으로 갱신됐다. 바뀐 값은 `y` **하나뿐**이고 전부 −12 다.

**앉히는 자리**: `seatModuleDepth` 하나가 규칙을 갖고, `persistPlannerState`
(저장 전)와 `loadModules`(열 때)가 부른다. 부르는 쪽마다 챙기면 한 곳은 빠진다.
멱등이라 여러 번 불러도 안전하다.

**옛 모듈도 앞선으로 온다** (W12-34) — `areaId` 가 없으면 `areaOfModule` 의
X 겹침 추정을 쓴다. 옛 설계의 상부장이 하부장 영역에 걸쳐 있으면 그 영역의
앞선에 맞춰지므로, 상부장 앞면이 하부장 앞면과 같은 평면에 온다.

**회전 영역도 앞선으로 온다** (W12-37) — §9.8 이 좌표 규약을 배치 단계에 맞춘
뒤로 `m.y`·`m.D` 는 어느 회전에서나 깊이 축이다. 그 전에는 회전 다리 모듈이
`m.y` 를 런 좌표로 쓰는 것처럼 보여 1500mm 미끄러졌는데, 규약이 어긋나 있었기
때문이지 데이터가 다른 뜻이어서가 아니었다.

> 실측 — ㄱ자 픽스처의 회전 다리 모듈이 영역 밖 `y2150` 에서 영역 안 `y650`
> 으로 들어왔다. 영역 이탈 1건 → **0건**.

**조립체가 영역보다 깊으면** 앞선에 맞출 자리가 없다 — 뒤에 붙고 도어가 앞으로
넘는다. 옛 설계에 몸통이 영역만큼 깊은 것이 있다 (`addModuleToArea` 의
`영역 D − 도어` 규칙 이전).

`areaLimitsFor` 도 같이 고쳤다. 예전엔 모듈이 영역 **가운데** 있다고 가정해
어림했는데 실제로는 뒤에 붙어 있었으니 틀린 값이었다. 회전이 없으면 실제
좌표로 잰다.

> 우측 패널도 같이 손봤다. 섹션이 일곱이라 다 펴면 화면보다 길다 — 스크롤은
> 원래 됐지만 **마지막 줄이 바닥에 딱 붙어** 잘려 보였다. 끝에 여백 28px 를 주고,
> 섹션 머리말을 `sticky` 로 붙여 스크롤 중에도 어디인지 보이게 했다.

### 9.7 냉장고장은 좌우 EP 가 기본 (W12-35)

냉장고장은 냉장고와 벽 사이에 세우는 장이라 **옆면이 늘 드러난다** — 마감이
없으면 몸통 PB 가 그대로 보인다. 나란한 장에 가려지는 다른 섹션과 다르다.

`DEFAULT_EP_SECTIONS = ['fridge']` 하나가 목록을 갖고, `applyDefaultAreaFinish`
가 세운다. **기본값이지 강제가 아니다** — 이미 그 쪽에 마감재가 있으면 두지 않고,
사람이 '없음' 으로 뗀 것을 되살리지 않는다.

| 부르는 자리 | 언제 |
|---|---|
| `+ 모듈 추가` | 그 영역의 **첫 모듈**일 때만 |
| `autoCalcArea` / `autoCalcStack` | 채운 뒤 (다담 표준으로 다시 짜는 자리) |

마감재는 폭을 내놓을 모듈이 있어야 서므로(§9.2) 반드시 **영역을 채운 뒤**에 부른다.
스택 영역(냉장고장 3단)은 `setStackAreaFinish` 가 단들을 함께 줄인다.

> 실측: 영역 W900 → 냉장고장 720 + EP 20×2, 호스트 680. EP 는 2300×700×18T.

### 9.8 회전 좌표는 배치 단계 규약을 따른다 (W12-36)

**배치 단계가 정본이다.** `mockup-shell.html` 의 `getRotatedCorners` 는 사각형을
**자기 중심**(`x + w/2, y + h/2`)으로 돌린다. 저장되는 것은 회전 **전** 좌표
(`x, y, w, h`)와 `rotation` 이다.

구조 단계는 다섯 곳에서 `(x, y)` 를 그대로 시각 좌상단으로 쓰고 폭·깊이만
맞바꿔 왔다. 어긋난 양이 정확히 **(W − D)/2** 다.

```
ㄱ자를 겹쳐 트리밍한 세로 다리 — rect(1562.5, 837.5, 1800, 125) rot 90

  배치가 그리는 자리   X[2400, 2525]  Y[0, 1800]
  구조가 그리던 자리   X[1562, 1687]  Y[0, 1800]   ← (1800−125)/2 = 837.5 만큼 밀림
```

두 다리가 서로 다른 자리로 흩어져 ㄱ자가 안 맞던 것이 이것이다.

**모듈의 회전축은 자기 중심이 아니라 속한 영역의 중심이다.** 영역이 통째로
도는 것이라, 모듈을 제 중심으로 돌리면 영역 밖으로 흩어진다.

계산은 `planeBoxOf(o, pivot)` 하나로 모았다 — 영역은 축을 안 주고(제 중심),
모듈은 `modulePlaneBox(m)` 이 영역 중심을 넘긴다. 90 배수는 정확값을 써서
`Math.sin(π/2)` 같은 부동소수 오차가 안 생긴다 (배치 단계와 같은 처리).

| 고친 곳 | 무엇 |
|---|---|
| `areaFrontRect` | 정면도 영역 사각형 |
| `fitFrontView` · `viewX` | 정면도 X 매핑·정렬 |
| `renderAreas3D` | 영역 상자 — 이제 모듈처럼 **회전시킨다** |
| `fitCameraToAreas` | 3D 카메라 bounds |
| `renderAll3D` | 모듈 메시 위치 — 영역 축으로 돈다 |

회전이 없으면 계산 결과가 예전과 **동일**하다 (`swap` 없음, 축 = 제 중심).
골든 3/3 바이트 동일.

> 실측(트리밍한 ㄱ자, 자동계산 후): 모듈 5개 전부 영역 안. 두 다리가 X 2400 에서
> 맞닿는다.

### 9.9 상몰딩 앞면 = 도어 앞선 (W12-37)

상몰딩을 몸통 앞면에 맞추면 도어 두께만큼 안쪽으로 들어가 **앞선이 계단처럼
꺾인다**. 상몰딩은 그 선을 따라가는 마감이라 도어 앞선에 맞아야 한다.

```
        ┌──── 상몰딩 ────┐   앞면 = 몸통 앞 + 18   (= 도어 앞선 = 배치 공간 앞선)
        │                │
        ├──── 도어 ──────┤   앞면 = 몸통 앞 + 18
```

깊이만 `m.D + DOOR_T` 로 늘리고 중심을 `DOOR_T/2` 앞으로 옮긴다 — **뒷면은
몸통 뒷면 그대로**다. 도어 높이는 몸통 높이라 상몰딩이 시작하는 지점에서
끝나므로 세로로 겹치지 않는다 (§9.4).

상판(`addTopPanel`)·좌대(`addPedestal`)는 그대로다.

> 실측(상부장 D320): 몸통 앞 382 · 도어 앞 400 · **상몰딩 앞 400** · 영역 앞 400.

### 9.10 받침(다리발 · 좌대)과 상판 (W12-38)

**받침** — 몸통을 바닥에서 받치는 부재. 다리발이거나 좌대이고 **한 모듈에 하나만**
선다. 예전엔 섹션이 정해 버려 사람이 고를 수 없었다.

```
받침  [다리발 ▾]
  └ 다리발 (mm)  150
```

| | |
|---|---|
| 기본값 | 하부장 등 → 다리발 · 키큰장/냉장고장 → 좌대 (**예전 동작 그대로**) |
| 고르면 | `s.baseKind` 에 남는다. `legHOf` 가 그 선택을 따라 0 을 낸다 |
| 상부장 | 받침이 없다 — 매달린다 |

`heightPartsOf` 의 받침 슬롯 하나가 두 부재를 대신한다. 안 고르면 섹션 기본값이라
골든이 바이트 동일하다.

**상판** — **배치 공간 단위** 부재다. 런 전체를 한 장이 덮는다. 모듈 폭에 맞추면
모듈마다 이음매가 생기고 마감재 자리가 빈다.

- 폭·깊이를 **영역**에서 받는다 (`area.W` × `area.D`)
- 영역의 **첫 모듈에만** 그린다 — 모듈마다 그리면 겹쳐 쌓인다
- 자리는 영역 중심. 영역과 모듈이 같은 각으로 도므로 회전 전 차이를 로컬 offset 으로 쓴다

**영역 패널이 모듈까지 적는다.** 영역에만 적어 두면 값이 정면도·3D·BOM 에 닿지
않는다 — 이 저장소가 여러 번 밟은 함정이다. `applyAreaHeightPart` 가 그 영역의
모든 모듈 구조에 함께 쓰고, 마감재 모듈은 건드리지 않는다.

영역 높이 항목은 이제 셋이다 — **받침(선택) · 상판 · 상몰딩**. 그 섹션에 없는
부위는 숨기지 않고 막고 이유를 적는다 (§9.2 의 항목 수 통일).

> 실측: 영역 W2400 에 모듈 3개(960·960·480). 상판 30 → 영역·모듈 셋 모두 30,
> 3D 에 2400 짜리 한 장. 받침을 좌대로 → 다리발 0 · 좌대 60 (세 모듈 모두).

### 9.11 배치 공간이 높이의 제한 기준 (W12-39)

모듈 높이는 **배치 공간에서 받는다.** 예전엔 섹션 기본값(하부장 850)을 써서,
영역이 870 이어도 모듈은 850 이었다 — 배치에서 정한 치수가 구조에 안 닿았다.

```
배치 공간 870
  ├ 다리발 150
  ├ 상판    12
  └ 몸통   708
```

`addModuleToArea` 가 `area.H` 를 그대로 쓴다. 섹션이 영역과 다르면 그 섹션 기본
높이를 쓰되 영역을 넘지 않는다. 스택(키큰장·냉장고장)은 `autoCalcStack` 이
영역 높이를 단으로 나누므로 그대로다.

**상판은 옵션이 아니라 높이 모델의 한 부위다.** 새 모듈이 `s.topT = 0` 으로
눌러 놓던 것을 없앴다 — `heightPartsOf` 의 기본값(12)이 그대로 산다.

**영역 패널은 그 섹션이 가진 부위만 낸다** — 하부장 영역에 상몰딩 칸이 뜨지
않는다. 모듈 패널은 처음부터 그랬으므로 두 패널이 이제 같다. (§9.2 의 "항목 수
통일" 은 팔레트 시절 규칙이었다. 없는 부위를 막아 두는 대신 아예 안 내는 편이
읽기 쉽다.) 판단은 `heightPartsOf` 하나가 하고, 죽은 `areaPartInfo` 는 지웠다.

영역 패널이 높이 구성을 적는다:

```
받침  [다리발 ▾]
  └ 다리발 (mm)  150
상판 (mm)        12
─────────────────
몸통             708
배치 공간 높이   870 mm
전체 870 = 다리발 150 + 상판 12 + 몸통 708
```

> 실측: 하부장 영역 870 → 항목 `[legH, topT]`, 모듈 H 870, 몸통 708.
> 키큰장 영역 2300 → 항목 `[pedestalH, moldingH]`, 전체 2300 = 좌대 60 +
> 상몰딩 60 + 몸통 2180.

### 9.12 걸레받이 (W12-41)

하부장 다리발 자리를 앞에서 막는 판. **치수는 BOM 이 정본이다** —
`js/detaildesign/extractors.js` 가 이미 이렇게 잡고 있었다:

| | |
|---|---|
| 재료 | MDF **18T** |
| 폭 | 런 전폭 (`effectiveW`) — 상판과 같이 **배치 공간 단위** |
| 높이 | **다리발 − 5** — 5mm 는 바닥 여유, 판은 다리발에 걸린다 |
| 자리 | **앞선에서 40mm 안쪽** (발끝 자리) |

앞선은 배치 공간 앞면이고 도어 앞면과 같은 평면이다 (§9.6·§9.9).
좌대를 고르면 다리발이 없으므로 걸레받이도 서지 않는다 (§9.10).

**앞줄 다리발이 걸레받이 뒤로 물러난다.** `LEG_INSET` 이 25 라 그대로 두면
15mm 겹친다 (실측). 실제로도 걸레받이는 이 다리에 클립으로 걸리므로 그 뒤가
제자리다. `toeKickBackZ` 하나가 두 곳(걸레받이·다리발)에 같은 평면을 준다.

> `addLegs` 의 `zBack` 은 이름과 달리 **월드 앞쪽**이다 (+Z 가 앞). 이름은
> 그대로 두고 주석으로 밝혔다 — `side` 값이 클릭 안내에 쓰인다.

**폭은 영역 전폭이 아니라 모듈 구간이다** (W12-43). 마감재(몰딩·휠라)는 바닥까지
내려오므로, 영역 전폭으로 잡으면 걸레받이가 그 판을 **관통한다** (실측 18mm).
상판은 마감재 **위**를 지나가므로 영역 전폭 그대로다.

> 실측(영역 2400×650×870, 마감재 없음): 걸레받이 `X[0,2400] Y[5,150] Z[592,610]`.
> 전체 쌍 겹침 16건으로 그대로 — 새 겹침 없음.

**BOM 연결은 아직이다.** `extractors.js` 는 상세설계 단계의 자재 추출기이고
BOM/Materials 도메인 소유라 이 변경에 포함하지 않았다 — 플래너가 그리는 것과
BOM 이 뽑는 것이 이미 같은 규칙을 쓰므로 값은 어긋나지 않는다.

### 9.13 마감재 높이는 종류가 정한다 (W12-42)

셋이 다 같은 높이가 아니다. `finishingSpanOf` 하나가 세로 범위를 낸다.

| 마감재 | 세로 범위 | 왜 |
|---|---|---|
| **EP** | **상판 아래에서 멈춘다** | 상판이 그 위를 덮고 지나간다 (W12-44) |
| **몰딩** | 같다 | 상판 위로 넘어갈 수 없다 |
| **휠라** | **인접한 도어와 같다** | 도어 옆에 서는 것이라 그 선을 따라간다 |

상판이 없는 섹션(상부장·키큰장·냉장고장)은 뺄 것이 없어 배치 공간 전체가 된다
— 냉장고장 2300 이면 EP 도 2300 이다 (§9.2).

```
하부장 영역 870 · 상판 12 · 목찬넬 도어

  상판     858 ─ 870
  몰딩       0 ─ 858     ← 상판 바닥에서 멈춘다
  휠라     150 ─ 828     ← 도어와 같다 (목찬넬이라 위로 30 물러남)
```

휠라는 `doorSpanOf` 가 내는 범위를 그대로 쓴다 — 몸통 바닥에서 시작해 몸통
상단에서 끝나되 목찬넬이면 위로 30(§9), 도어 내림이면 아래로 15(§9.1) 나간다.

상판이 없는 섹션(상부장·키큰장·냉장고장)은 몰딩이 전체 높이 그대로다.
스택 영역의 휠라는 단이 셋이라 "인접 도어" 가 하나로 정해지지 않아 전체 높이를 쓴다.

**만들 때와 다시 맞출 때가 같은 함수를 지난다** — `addFinishingToArea` ·
`setStackAreaFinish` · `setModuleFinish` · `syncFinishingsToAreas` 넷 다
`finishingSpanOf` 를 부른다. 두 벌로 두면 영역을 고쳤을 때 한쪽만 따라온다.

> 실측: 영역 870 → 몰딩 Y[0,858] · 휠라 Y[150,828] · 상판 Y[858,870].
> 영역을 900 으로 바꾸면 몰딩만 888 로 따라오고 휠라는 678 그대로다 (도어가 안 바뀌었다).

### 9.14 마감재를 넣으면 모듈이 줄어든다 (W12-43)

EP·몰딩·휠라 **모두** 모듈 폭을 그만큼 가져간다. 영역 총 폭은 그대로다.

```
영역 2400
  마감재 없음        모듈 2400
  + 몰딩(좌) 60      몰딩 [0, 60]    모듈 [60, 2400]
  + 휠라(우) 60      휠라 [2340, 2400]  모듈 [60, 2340]
```

> 이 부분은 `setModuleFinish` 가 처음부터 하고 있었다 — 실측으로 확인했다
> (2400 → 2340 → 2280, X 구간 겹침 0).

실제로 겹치던 것은 **걸레받이**였다. 영역 전폭으로 서서 바닥까지 내려오는
몰딩을 18mm 관통했다. §9.12 대로 폭을 모듈 구간으로 좁혀 해결했다.

### 9.15 마감재가 셀 폭을 데려간다 (W12-44)

마감재를 붙이면 모듈 폭은 주는데 **저장된 셀 폭(`areaWidths`)이 그대로 남았다.**
도어가 옛 폭으로 그려져 옆 모듈·마감재를 파고들었다.

```
영역 2400, 자동계산 3칸 → 960 / 960 / 480, 양 끝에 EP 20

  모듈      lower-0  W 960 → 940
  저장 셀폭 [960]  ← 그대로
  도어      X[502, 978]   vs  lower-1 도어 X[962, 1438]   → 16mm 겹침
```

`rescaleCellWidths` 가 폭이 바뀔 때 셀 폭을 **같은 비율로** 줄인다. 손으로 폭을
고치는 길(`applyModuleDim`)은 배열을 **비워** 균등분할로 되돌리지만, 마감재는
갯수·양문 배치를 바꾸는 것이 아니라 폭만 깎는 것이라 비율이 맞다. 반올림 오차는
마지막 칸이 흡수한다 — 합이 폭과 어긋나면 또 넘친다.

붙일 때(`setModuleFinish`)·뗄 때(`removeModuleFinish`)·스택(`setStackAreaFinish`)
셋 다 지난다.

> 실측(하부장 2400 자동계산 + 양 끝 EP): 마감재·도어가 얽힌 겹침 8건 → **2건**.
> 남은 2건은 목찬넬 지면판 ↔ 처짐방지목 6.1mm 로, 이 항목과 무관한 기존 것이다.

### 9.16 마감재가 자리를 바꾸면 균등 분배 (W12-45)

마감재를 붙이면 그 폭만큼 모듈 자리가 준다. 예전엔 **끝 모듈 하나만** 줄어
칸이 들쭉날쭉했다. 이제 남은 공간을 다시 고르게 나눈다.

```
자동계산    960 | 960 | 480                    편차 480
+ EP 20     [EP] 793 | 793 | 794               편차 1
+ 몰딩 60   [EP] 773 | 773 | 774 [몰딩]        편차 1
− EP        780 | 780 | 780 [몰딩]             편차 0
                                              합은 늘 영역 폭 2400
```

- **고정 모듈은 폭을 지킨다** — 사람이 정한 치수를 자동 동작이 덮지 않는다.
  그 나머지만 나눈다.
- **한 칸이라도 도어 최소폭보다 좁아지면 아무것도 하지 않는다.** 반쯤 좁혀
  놓는 것이 더 나쁘다.
- 셀 폭도 같이 데려간다 (§9.15).
- 스택 영역은 단이 겹쳐 서므로 나눌 것이 없다 — 건드리지 않는다.

**폭 판정도 나눈 뒤 값으로 한다.** 호스트 하나만 보고 막으면 세 칸으로 나누면
들어갈 것을 못 붙인다 — 1200/3 = 400 에서 몰딩 60 을 호스트에서만 빼면
340 < 350 이라 거절되지만, 나눈 뒤에는 (1200−60)/3 = 380 이라 들어간다.
`evenWidthAfterFinish` 가 그 값을 낸다.

## 10. 미해결 — 학습으로 넘기기 전에 정해야 할 것

| 항목 | 내용 |
|---|---|
| **상판 12mm** | 엔진(선반)은 상판을 안 빼고, 높이 패널은 뺀다. 두 몸통 값이 다르다 |
| **다리발 120** | `SINK_LEG` 주석의 "또는 120" 이 언제 쓰이는지 규칙이 없다. DB 는 120~150 을 유효 범위로 둔다 |
| **처짐방지목 60 vs 70** | OBJ 실측 60, 마스터 문서·DB 70. 현재 OBJ 채택 |
| **도어 방향** | 단문은 전부 `left`. W9-72 의 "인접 도어 반대" 교대 규칙은 폐기됐고 대체 규칙이 없다 |
| **BOM 목찬넬 따내기** | 플래너는 §9 대로 그리지만 `extractors.js` 의 측판은 여전히 통짜다. 가공 주석이 없다 |
| **상부장 목찬넬** | 매립 방식이 하부장과 다르다. 규칙 미정 |

> **90° 회전 영역** 은 §9.8 에서 해결됐다 — 규칙이 없던 것이 아니라 배치 단계의
> 규약을 구조 단계가 잘못 읽고 있었다. 남은 이탈은 손으로 쓴 옛 픽스처뿐이다
> (모듈이 어느 영역에도 안 들어가는 좌표를 갖고 있다).

이것들은 **규칙이 없는 것이지 규칙이 숨어 있는 것이 아니다.**
학습 모델에 맡기기 전에 사람이 정해야 한다.

> 손잡이 선택지는 해결됐다 — `channel`(알루미늄 매립 12mm) / `wood-channel`(목찬넬,
> §9) / `c-channel` / `push` 로 나뉜다. 다만 `push` 는 `ACTIVE_RULES.md` §15 가
> **금지**한 방식이라 UI 에 남아 있는 것이 맞는지 확인이 필요하다.
