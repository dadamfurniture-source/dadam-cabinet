# 사진 모드 (P1·P2 — `photo-bg.js` · `photo-mode.js`)

> 계획: `docs/01-plan/photo-composite.plan.md` §4.3 · §5 P1 (`agent/photo-background-ui`) · P2 (`agent/photo-shadow-light`).
> 수학은 P0: `docs/02-design/features/photo-solve.md`. 3D Planner 도메인, 구조 페이지의 **디테일 모드 안의 모드**다.

## 무엇이 되는가

방 사진을 올리고 사진 위 바닥에 사각형을 대충 놓으면, 플래너의 가구가 **그 사진의 원근 그대로** 사진 위에 선다.
사각형을 끌거나 미세조정을 누를 때마다 합성이 즉시 다시 그려진다.

```
방 사진 ─→ <img> 가 3D 캔버스 뒤에                scene.background = null → alpha 버퍼로 비친다
사각형 ─┬─→ photo-solve 가 카메라 역산 ─→ **별도 카메라**로 레터박스 안에 렌더
배치 공간 ┘     (실제 치수는 여기서 자동으로)         화면 카메라·OrbitControls 는 건드리지 않는다
```

P2 가 여기에 **그림자와 빛과 톤**을 더했다 (아래 "P2" 절). 이제 가구가 사진 바닥에 그림자를 드리운다.

**아직 하지 않는 것**: 저장(P3), 가림(P4), 문서 싣기(P5), AI 마무리(P6).
지금은 **화면에 보이는 것까지**다. 새로고침하면 사각형·화각·미세조정·빛·톤은 남고 사진만 다시 올리면 된다
(사진은 비공개 버킷에 올라가야 하는데 그 배관이 P3 이다 — 계획 §4.5).

## 왜 "대충" 으로 충분한가 (2026-09-17 결정)

바닥 사각형은 **가구가 설 대략적인 위치**를 가리킬 뿐이다. 가구의 치수는 언제나 플래너의 배치 공간에서 온다
(계획 §9-2). 그래서 사용자에게 "정확히 찍으세요" 라고 요구하지 않는다 — 대신:

| 설계 | 이유 |
|---|---|
| 처음부터 사다리꼴이 놓여 있다 (`quadDefault`) | 빈 사진에 점을 찍으라 하면 어디부터 찍을지 고민한다. 밀기만 하면 되게 한다 |
| 끄는 **동안** 매번 다시 푼다 | 합성이 눈앞에서 따라오면 "맞았다" 를 눈으로 안다 |
| 미세조정(X·Z·회전) | 사각형을 더 정확히 찍는 대신 가구를 밀어 맞춘다 |
| 상태 한 줄 (`quadHealth`) | 맞음 / 대충 맞음 / 틀림 을 재투영 오차와 함께 사람 말로 |
| 화각 자동 맞춤 (`fitFov`) | 화각 슬라이더를 손으로 더듬지 않아도 된다 |

P0 이 측정한 근거: 손이 ±3px 흔들리면 3600×700 바닥에서 카메라가 262mm(중앙값) 어긋난다. 요구할 수 없는 정밀도다.
같은 손떨림도 2400×1500 에서는 62mm 다 — **너른 사각형이 얇은 띠보다 약 4배 정확하다.** 그래서 패널이
"가구가 설 자리 전체를 잡으세요" 라고 안내하고, 얇은 사각형에는 그 안내를 따로 붙인다.

## 미세조정은 씬이 아니라 **사각형**을 움직인다

`plannerPhotoBgSolveRect(rect, nudge)` 가 사각형의 원점을 `(−dx, −dz)` 로 옮기고 회전을 `−dRot` 한다.
그 사각형으로 풀면 카메라가 그만큼 옮겨 풀리고, 세계에 고정된 가구는 사진 위에서 정확히 `(+dx, +dz)` 만큼
움직여 보인다. 모듈 mesh 를 한 톨도 건드리지 않으므로 BOM·도면·골든 페이로드와 어긋날 수가 없다 (불변식 I1).

## 귀퉁이 순서 — 왜 이름표를 붙이는가

**0 뒤-좌 · 1 뒤-우 · 2 앞-우 · 3 앞-좌** (photo-solve 의 정본 순서. "뒤" 는 평면도 위쪽, 벽 쪽).

직사각형은 180° 회전에 대해 자기 자신이다. 그래서 대각선 반대 귀퉁이에서 시작하면 **재투영 오차가 정확히 0 인,
방 반대편에서 본 카메라**가 나온다 (photo-solve.md "이 수학이 못 하는 것" 4번 — 실측 위치 오차 7835mm, RMS 0.0px).
숫자로는 막을 수 없다. 그래서 두 가지를 같이 한다:

1. **이름표** — 편집기의 네 손잡이에 앞/뒤·좌/우 이름이 붙어 있다. 순서를 보여 주는 것 말고는 방법이 없다.
2. **물리 검사** (`quadHealth`) — 카메라가 바닥 아래 · 눈높이 300mm 미만 또는 4000mm 초과 · 30m 밖 ·
   사각형 **뒤**(벽 쪽)에 서면 "틀림" 이다. 180° 어긋남은 이 중 하나에 반드시 걸린다.

두 장치는 서로를 대신하지 못한다. 이름표만으로는 실수를 못 잡고, 물리 검사만으로는 왜 틀렸는지 알려 주지 못한다.

## 상태 등급

| 등급 | 언제 | 화면 |
|---|---|---|
| `good` 맞음 | 재투영 RMS ≤ 긴 변의 0.25% (최소 4px) | 초록 · `맞음 · 재투영 오차 3px` |
| `rough` 대충 맞음 | ≤ 긴 변의 1% (최소 12px) — 계획 §2 의 완료 기준 | 노랑 · `사각형을 조금 더 넓게 잡아 보세요` |
| `bad` 틀림 | 그보다 크거나 **물리 검사에 걸림** | 빨강 · 무엇을 확인할지 |

물리 검사는 등급 계산보다 **먼저** 온다 — 재투영 오차가 0 인데도 틀린 경우가 실재하기 때문이다.

## 화각 세 갈래

| 상황 | 하는 일 |
|---|---|
| 소실점으로 풀린다 (`method:'vanishing'`) | 그대로 쓴다 |
| 정면 사진이라 퇴화 (`method:'assumed'`) | **자동으로 훑어** 재투영 오차가 가장 작은 화각을 고르고, 그렇게 했다고 적는다 |
| 사용자가 슬라이더를 움직였다 | 그 값으로 고정 |

근거는 P0 의 측정이다 — 진짜 45°/60°/75° 를 60° 로 가정했을 때 재투영 RMS 가 158.8 / 0.0 / 133.2 px 로 갈렸다.
**틀린 화각은 오차로 드러난다.** 그래서 훑기가 먹힌다.

## 복원 규율 (불변식 I2)

`PlannerDetail.applyScene` 의 규율 그대로다 — **바꾸기 전 값을 전부 적어 두고, 나갈 때 그대로 되돌린다.**

| 적어 두는 것 | 왜 |
|---|---|
| `scene.background` | 사진이 비치려면 null 이어야 한다 (G1) |
| `controls.enabled` | 사진 모드에서 궤도·줌은 끈다 — 카메라는 사진의 것이다 |
| 바닥판·그리드·원점 마커의 `visible` | 사진 위에 깔리면 바닥이 두 겹이 된다 (G5). 씬 자식이라 `entityKind` 이름표로 찾는다 |
| 도어 테두리 막대의 `visible` | 사진 위의 검은 선은 만화처럼 읽힌다 (G7) |
| renderer 의 viewport·scissor·scissorTest | 레터박스로 잘라 그리기 때문 |
| (P2) 조명·그림자·노출·받개 | 아래 "P2 — 복원 규율 (G6)" 에 표가 따로 있다 |

씬은 `renderAll3D` 가 언제든 다시 만든다. 그래서 숨기기는 **매 프레임** 확인하고, 원래 값은 처음 본 것만 적는다.
디테일 모드를 나갈 때 `PlannerDetail.exit` 가 사진 모드를 **먼저** 내보낸다 — 안 그러면 구조 모드가 사진 모드의 씬을 물려받는다.

`__tests__/photo-mode.test.js` 가 들어가기 전 값을 통째로 찍어 두고 나온 뒤와 대조한다. "정말 바뀌었는지" 를
먼저 확인해서, 아무것도 안 바뀌는 버그가 복원 시험을 초록으로 통과시키지 못하게 한다.

## 레터박스 — 사진·렌더·편집기가 같은 사각형

사진의 종횡비와 캔버스의 종횡비는 다르다. 캔버스 전체에 그리면 원근이 늘어나 합성이 통째로 어긋난다.
`plannerPhotoModeBox(canvasW, canvasH, aspect)` 가 캔버스 안에 사진 종횡비의 상자를 잡고, 셋이 **그 상자를 공유한다**:

- 렌더 — `setViewport`/`setScissor` (three 는 y 를 아래에서 세므로 `plannerPhotoModeViewport` 가 뒤집는다)
- 사진 `<img>` — 같은 자리·같은 크기 (CSS px)
- 편집기 `<svg>` — 같은 자리, `viewBox` 도 상자 크기

## 사진 들이기

- **EXIF 방향**: APP1 블록을 직접 읽어 태그 0x0112 를 찾는다 (의존성 0, `photo-solve.js` 가 8×8 을 직접 푼 것과 같은 이유).
- **두 번 돌리기 방지**: 요즘 브라우저는 `<img>` 디코딩 때 EXIF 방향을 스스로 적용한다 (CSS `image-orientation: from-image` 가 기본값).
  방향 5~8 은 가로·세로가 맞바뀌므로 JPEG 안에 저장된 크기(SOF)와 디코딩된 크기를 비교하면 **확실히** 안다.
  2·3·4 는 크기가 그대로라 비교로 못 가르고, CSS `image-orientation` 지원 여부를 대리 신호로 쓴다.
- 긴 변 4096 으로 줄이고 JPEG 0.9 로 다시 인코딩한다. 방향 세우기와 줄이기는 **한 번의 캔버스 변환**으로 — 두 번 그리면 화질이 두 번 깎인다.
- JPEG·PNG 만, 20MB 까지. 거절 이유는 한국어 그대로 화면에 뜬다.

# P2 — 그림자 · 빛 · 톤 (2026-09-17, `agent/photo-shadow-light`)

가구가 바닥에 그림자를 드리우지 않으면 사진 위에 **떠 보인다**. P2 는 그 하나를 고치는 단계다.
우측 패널의 「그림자 · 빛 · 톤」 묶음이 전부이고, P1 의 사진·사각형·미세조정 묶음은 그대로다.

## 슬라이더 아홉 칸

| 칸 | 범위 | 무엇을 바꾸는가 |
|---|---|---|
| 그림자 | 0 ~ 0.9 | 받개(`ShadowMaterial`)의 `opacity`. 0 이면 받개가 아예 안 보인다 |
| 부드럽기 | 0 ~ 8 | 주광의 `shadow.radius` (**텍셀** 단위 — 아래 "그림자 품질") |
| 빛 방향 | 0 ~ 360° | 방위각. 0° = +Z(앞) · 90° = +X(오른쪽) |
| 빛 높이 | 5 ~ 85° | 고도. 90° 에 가까울수록 그림자가 짧다 |
| 빛 세기 | 0 ~ 4 | 주광 `intensity`. 채움 직사광은 그 1/3 로 반대쪽에서 따라간다 |
| 채움 | 0 ~ 2 | 주변광 `intensity`. 그림자 안쪽이 새카맣게 죽지 않게 |
| 노출 | 0.2 ~ 3 | `renderer.toneMappingExposure` |
| 색온도 | −100 ~ +100 | **조명 색** (아래 "색온도는 왜 조명 색인가") |
| 틴트 | −100 ~ +100 | 같은 자리. + 자홍 · − 초록 |

값은 `PlannerPhotoBg.state.light` · `.grade` 에 계획 §4.4 의 컬럼 모양 **그대로** 들어간다 —
P3 이 이 객체를 손대지 않고 행에 넣을 수 있게. 한계표(`PLANNER_PHOTO_BG_LIGHT_LIMITS` ·
`..._GRADE_LIMITS`)가 기본값·범위·슬라이더 눈금의 **유일한 정본**이라 두 군데서 어긋날 수가 없다.

**P1 때 저장된 상태에는 이 두 칸이 아예 없다.** 그래서 정규화는 빠진 칸을 조용히 기본값으로 채운다
(`plannerPhotoBgClampBag`). 옛 저장본이 그대로 열린다.

## 기본값이 "지금 밝기 그대로" 인 이유

사진 모드는 디테일 모드 **안에서만** 열린다. 그 모드의 `applyScene` 이 환경광을 넣으면서 직사광·주변광을
절반으로 낮춰 둔다 (init3D 의 1.8·0.6 → 0.9·0.3). 그래서 빛 세기·채움의 기본값도 **0.9·0.3** 이고,
방향 기본값도 init3D 의 주광 (5000, 8000, 5000) 과 같은 쪽(방위 45° · 고도 48°)이다.
사진 모드에 들어가는 것만으로 밝기가 튀거나 그림자가 홱 돌면 "내가 뭘 잘못 눌렀나" 가 된다 —
**들어가도 보기는 그대로고, 그때부터 사용자가 민다.**

## 그림자 받개

`y = 0` 의 `ShadowMaterial` 평면이다. 그림자만 알파로 남기므로, 투명 배경 렌더 **한 장**에
가구와 그림자가 알파까지 맞게 함께 담긴다 (계획 §4.3 정정 — 따로 뽑지 않는다).

- 크기 = 가구 발자국 + 여백(발자국의 0.9배, 최소 900mm). 기울어진 빛의 긴 그림자를 받으려면 넓어야 한다.
- `entityKind: 'shadow-catcher'` — `plannerCaptureBoundsOf` 의 제외 목록에 **같은 문자열**로 들어 있다.
  안 빼면 가구보다 훨씬 넓은 평면이 경계에 섞여 렌더 프레이밍이 통째로 어긋난다 (계획 §1.4 G5).
- **씬의 자식**이라 `PlannerDetail.paintScene`(moduleGroup 순회)에도, 화면 클릭 레이캐스트
  (`intersectObjects(moduleGroup.children, true)`)에도 걸리지 않는다. 받개에 자재 재질이 얹히면
  그림자가 아니라 바닥판이 된다.
- `depthWrite = false` — y=0 에서 모듈 바닥면과 같은 평면에 놓이므로 깊이까지 쓰면 깜빡인다.
- 모드에 있는 동안만 씬에 있다. 나가면 빼고 지오메트리·재질을 버린다.

## 그림자 품질 — 무엇을 고르고 왜인가 (three r0.183 소스 근거)

**1. 프러스텀이 제일 크다 — 사실은 "품질" 이 아니라 "있느냐" 의 문제였다.**
`DirectionalLightShadow` 의 기본 카메라는 `OrthographicCamera(-5, 5, 5, -5, 0.5, 500)` 이다
(`DirectionalLightShadow.js:16`). 이 씬의 단위는 **mm** 이므로 그것은 10mm × 10mm, 깊이 500mm 짜리
상자다. 주광은 (5000, 8000, 5000) 에 서 있고 가구는 수천 mm 를 차지한다 — **하나도 안 들어간다.**
페이지가 `castShadow` 와 `shadowMap.enabled` 를 켜 두었는데도 화면에 그림자가 없던 진짜 이유가 이것이다.
사진 모드는 프러스텀을 **가구 바운즈**(대각선의 절반 × 1.15)에 맞추고 near/far 도 빛 ↔ 가구 거리에 맞춘다.
→ 계획 §9-7 로 올렸다: 구조·디테일 모드에도 켤지는 사장님이 볼 일이다. 여기서는 사진 모드만 고친다.

**2. 해상도.** 텍셀 크기 = 프러스텀 폭 / `mapSize`. 프러스텀을 맞춘 다음 `mapSize` 를 1024² → **2048²**
로 한 단계 올린다. 지도 한 장이 더 필요한 게 아니라 같은 한 장이 커지는 것이라 값이 싸다.
크기를 바꿀 때는 이미 만들어진 `shadow.map` 을 **버려야** 새 크기가 먹는다 (`_setMapSize`).

**3. 부드럽기는 `shadow.radius`, 그래서 그림자 지도는 `PCFShadowMap`.**
`radius` 를 읽는 셰이더는 PCF 와 VSM 뿐이다 — `WebGLProgram.js:344-352` 의 표에 없는 값은 전부
`SHADOWMAP_TYPE_BASIC` 로 떨어지고, BASIC 은 한 탭이라 radius 를 아예 안 쓴다. 그런데 페이지가 켜 둔
`PCFSoftShadowMap` 은 이 판에서 **폐기**됐다 — `WebGLShadowMap.render` 가 첫 렌더에 경고와 함께
`PCFShadowMap` 으로 바꿔 버린다 (`WebGLShadowMap.js:99-104`). 그래서 사진 모드는 `PCFShadowMap` 을
**명시하고** 나갈 때 원래 값으로 되돌린다.

**VSM 은 쓰지 않는다.** VSM 에서는 "모든 그림자 받개가 그림자를 **드리우기도** 한다"
(`constants.js:78`). 받개 평면이 사진 전체에 그림자를 드리워 합성이 통째로 죽는다. 더 부드럽지만 못 쓴다.

`radius` 의 단위는 텍셀이다 (`shadowmap_pars_fragment.glsl.js:132` — `radius = shadowRadius * texelSize.x`).
그래서 프러스텀을 좁힐수록 같은 값이 세계 단위로는 좁아진다. 접지면이 또렷해지는 쪽이라 원하는 방향이다.

## 색온도는 왜 조명 색인가

색온도는 렌더러 설정이 아니다. 후처리 합성기(`EffectComposer`)를 들이지 않고 정직하게 할 수 있는 일은
**빛의 색을 바꾸는 것**이다 — "이 방의 화이트밸런스가 다르다" 는 말은 실제로 그 방의 빛 색이 다르다는
뜻이니 물리적으로도 맞는 자리다. 색상 계수는 가장 큰 칸을 1 로 맞춰 **밝기는 건드리지 않는다**
(밝기는 세기 슬라이더 하나만 맡는다).

**한계**: 스스로 빛나는 재질(emissive·unlit)에는 안 먹는다. 패널에 그렇게 적어 두었다.

## 자동 제안 — 「사진에 맞추기」

사진 `<img>` 를 32×32 캔버스에 줄여 그리고 평균 RGB 를 읽는다 (`plannerPhotoModeSamplePhoto`).
사진은 blob: 객체 URL 이라 같은 출처이므로 캔버스가 더럽혀지지 않지만, `SecurityError` 는 막아 둔다 —
못 읽으면 조용히 null 이고 버튼이 서지 않는다. 패널 전체가 안 그려지는 일은 없어야 한다.

| 무엇 | 셈 |
|---|---|
| 노출 | `√(사진 평균 밝기 / 0.45)`. 0.45 = "노출 1 일 때 렌더의 평균 밝기" 가정 |
| 색온도 | `(R − B) / (R + B) × 300`, ±100 으로 자름 |
| 틴트 | 초록이 평균보다 높으면 자홍(−) 쪽으로 |

**제곱근을 씌우는 이유**: 제안은 정답이 아니다. 크게 밀어 놓고 사용자가 되돌리게 하느니, 덜 밀어 놓고
더 밀게 하는 편이 낫다. 밝은 사진은 노출이 1 보다 커지고 어두운 사진은 작아진다 — 방향만 맞히고 절반만 간다.

**올리자마자 적용하지 않는다.** 사진을 올리면 제안을 **적어 두기만** 하고 패널에 한 줄로 보여 준다.
「사진에 맞추기」를 눌러야 들어간다. 조용히 바꾸면 "내 설정이 사라졌다" 가 된다.

## 복원 규율 — 왜 조명 저장이 여기 있는가 (G6)

`planner-detail.js` 의 `applyScene` 은 조명의 **세기만** 적어 둔다. 그 모드는 세기만 건드리니 그것으로
충분하다. 사진 모드는 위치·타깃·그림자 설정까지 바꾸므로 그 목록으로는 되돌릴 수 없다.

**다른 도메인의 저장 목록을 넓히는 대신** 사진 모드가 `_savedLight` 를 따로 둔다 — 내가 바꾼 것은 내가
되돌린다. 소유권이 흐려지지 않고, 그 파일을 다른 세션이 고쳐도 여기가 깨지지 않는다.

| 적어 두는 것 | 왜 |
|---|---|
| `position` · `target`(과 그 **부모**) | 방위각·고도가 이것을 옮긴다. 타깃은 씬에 붙여야 three 가 `matrixWorld` 를 갱신한다 — 나갈 때 떼지 않으면 씬에 고아가 남는다 |
| `castShadow` | 그림자를 켠 직사광이 없으면 주광으로 삼으며 켠다 |
| `shadow.camera` 의 left/right/top/bottom/near/far | 위 "그림자 품질" 1 |
| `shadow.mapSize` · `radius` · `bias` · `normalBias` · `blurSamples` | 위 2·3 |
| `color` · `intensity` | 색온도·틴트·세기 |
| `renderer.shadowMap.type` · `.enabled` | 위 3 |
| `renderer.toneMappingExposure` | 노출 |
| 받개가 씬에 있는지 | 나가면 없어야 한다 |

`__tests__/photo-light.test.js` 가 들어가기 전 값을 통째로 찍어 두고 나온 뒤와 대조한다.
**"정말 바뀌었는지" 를 먼저 확인**해서, 아무것도 안 바뀌는 버그가 복원 시험을 초록으로 통과시키지 못하게 한다.

## 슬라이더를 끄는 동안 패널을 다시 그리지 않는다

`patch` → `onChange` → `paint` → `renderPanel` 은 패널 HTML 을 통째로 새로 만든다. 슬라이더를 잡고 있는
중에 그러면 **지금 잡고 있는 손잡이가 사라진다.** 그래서 `data-look` 핸들러만 `_skipPanel` 을 세우고,
이름표 글자(`_lookLabel`)만 바꿔 끼운다. 씬은 그대로 따라온다.

## 아직 못 하는 것 (P2 기준)

1. 색온도가 **스스로 빛나는 재질**에는 안 먹는다 (조명 색이므로).
2. 사진의 **빛 방향**을 자동으로 읽지 않는다 — 방위각·고도는 사람이 민다. 제안하는 것은 톤뿐이다.
3. 그림자 받개는 **바닥 하나**다. 벽에 지는 그림자는 없다 (계획 §9-1 이 바닥으로 정했다).
4. 구조·디테일 모드의 그림자는 그대로 없다 — 계획 §9-7.
