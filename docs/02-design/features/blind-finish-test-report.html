물끊기가 없다는 것 하나만 다르고, 나머지는 동일합니다.

03키큰장 — 코너 대상이 아닙니다

버그가 아니라 의도된 제외입니다. 근거를 셋 대 봅니다.

  1. 코드가 명시적으로 뺍니다. cornerPairs 의 첫 줄이 areas.filter(a => !a.isFinishing && !isStackedArea(a)) 입니다. 키큰장은 stackForArea 가 스택을 돌려주므로 후보에서 빠집니다.
  2. 전제가 안 맞습니다. 코너 계산은 "라인 하나에 모듈이 나란히 선다" 를 전제로 폭을 나눕니다. 스택은 단이 세로로 겹쳐 서고 세 단이 같은 x·같은 W 를 씁니다 (W12-22) — 나눌 가로 자리가 없습니다.
  3. 규칙 문서에 없습니다. corner.md 는 하부(§3.3)와 상부(§3.6) 멍장만 정합니다. 키큰장 코너 공식은 정의된 적이 없습니다.

실측도 같습니다 — 키큰장으로 ㄱ자를 그려도 cornerPairs() 가 빈 배열이고 자동계산 후에도 멍장이 서지 않습니다. 회귀로 잠갔습니다.

대신 마감재 경로는 정상입니다

스택 전용 코드(setStackAreaFinish)를 타며, 비움도 세 단이 함께 폭을 내놓습니다. 한 단만 줄면 나머지 단이 마감재를 뚫고 나오는데(W12-22), 그 규칙이 유지됩니다.

04점검하다 고친 것

한 건입니다. 이번 기능이 만든 누락이라 범위 안에서 고쳤습니다.

비움이 상판을 침범해 보였다

finishingSpanOf 는 마감재가 서는 높이를 정합니다. 몰딩·EP 는 영역 H − 상판 두께, 휠라는 도어 높이를 씁니다. 그런데 비움은 어느 가지에도 없어 폴백(영역 H)으로 떨어졌습니다.

05확인했으나 고치지 않은 것

둘 다 main 에도 있는 기존 결함입니다 — stash 대조로 확인했습니다.

① 코너에 마감재를 붙이면 멍장이 부품보다 작아진다 상부장에서도 확인

1차 보고 때 하부장에서 찾은 결함인데, 상부장에서도 똑같이 재현됩니다.

상부 전    카카스 846  멍+도어 846  차이 0   원장 0
상부 좌몰딩 카카스 786  멍+도어 846  차이 −60  원장 −50
재계산     카카스 806  멍+도어 806  차이 0   원장 0   ← 자동계산이 복구한다

원인은 setModuleFinish 가 isFixed 를 보지 않고 호스트(=멍장) 폭을 뺏는 것입니다. 자동계산을 다시 돌리면 복구되지만, 그 전에 BOM 을 뽑으면 경고 없이 카카스보다 60 큰 부품이 발주됩니다 — 멍장이 셀 폭 합 검사를 건너뛰기 때문입니다.

② 키큰장 스택 단은 자동계산 뒤에도 셀 구조가 없다

키큰장으로 BOM 을 뽑으면 단마다 "자동계산 전이라 3600mm 통짜로 잡혔습니다" 경고가 뜹니다. 자동계산을 실행했는데도 뜹니다 — 스택 단에 areaWidths 가 안 생기기 때문입니다. main 에서 동일하게 재현됩니다.

왜 이 PR 에서 안 고쳤나

둘 다 이번 기능(멍판 마감재 · 비움)이 만든 것이 아니고, 고치려면 마감재가 붙는 방식 자체를 손봐야 합니다 — 승인 범위 밖이라 판단했습니다. ①은 별도 문서 「코너 원장 어긋남」 에 원인 셋과 선택지를 정리해 두었습니다.

07결론

상부장 — 이상 없음

코너 인식 · 멍장 생성 · 멍판 마감재 · 라인 연동 · 원장 · 겹침 · BOM 끝단까지 하부장과 동일하게 동작합니다. 회귀 테스트로 잠갔습니다.

키큰장 — 코너 대상 아님 (설계상 제외), 마감재는 이상 없음

스택 영역이라 멍장이 서지 않는 것이 맞습니다. EP·몰딩·휠라·비움 모두 스택 경로로 정상 동작하며, 세 단이 함께 폭을 내놓는 규칙이 유지됩니다.

남은 위험 — 코너 끝 마감재

상부·하부 공통으로, 코너 쪽 끝에 마감재를 붙인 뒤 자동계산을 다시 돌리지 않고 BOM 을 뽑으면 멍장 카카스가 60 작게 발주됩니다. 별건이며 판단을 기다리고 있습니다.
