# 사진 속 사각형에서 카메라 역산 (P0 — `js/planner/photo-solve.js`)

> 계획: `docs/01-plan/photo-composite.plan.md` §4.1 · §4.2 · §5 P0 (`agent/photo-solve-core`).
> 3D Planner 도메인. **아직 화면은 없다** — P1 (`agent/photo-background-ui`) 이 붙인다.

## 무엇을 푸는가

방 사진 위에 **가구가 설 바닥 사각형** 네 귀퉁이를 찍으면, 그 사각형의 실제 치수(배치 공간에서 자동으로 온다)와
짝지어 **사진을 찍은 카메라**를 되찾는다. 그 카메라로 3D 를 렌더하면 사진과 원근이 맞는 가구가 나온다.

AI 가 아니라 기하다. 평면 ↔ 평면 대응 네 쌍이면 호모그래피가 유일하게 정해지고, 거기서 초점거리와 자세가 모두 나온다.
그래서 **GPU 없이 단위 시험으로 정확도를 증명할 수 있다** — P0 이 UI 보다 먼저인 이유다.

```
네 점 대응 ──▶ 호모그래피 H ──▶ 소실점 직교 조건 ──▶ 초점거리 f ──▶ 평면 자세 분해 ──▶ R·t ──▶ three 카메라
                                     (안 되면 method:'assumed')
```

## 수학

### ① 호모그래피 — `plannerPhotoHomography(src, dst)`

`dst ≈ H·[src;1]` (동차 좌표, 마지막 성분으로 나눈다). 미지수 8개(`h₈ = 1` 로 고정), 대응 하나가 식 두 개:

```
[u v 1 0 0 0 −xu −xv]·h = x
[0 0 0 u v 1 −yu −yv]·h = y
```

8×8 을 **부분 피벗팅 가우스 소거**로 직접 푼다 (`plannerPhotoSolveLinear`). 의존성을 들이지 않는 것은
`planner-capture.js` 가 sha-256 을 직접 쓴 것과 같은 이유다 (`planner-capture.js:134`).

양쪽 점 무리를 **Hartley 정규화**(중심 0 · 평균 거리 √2)한 뒤 풀고 되돌린다: `H = T_dst⁻¹ · H' · T_src`.
mm(수천)과 px(수천)를 같은 계에 섞으면 조건수가 나빠져 왕복 오차가 눈에 보이기 때문이다. 특이하면 `null`.

### ② 초점거리 — `plannerPhotoFocal(H, cx, cy)`

바닥 사각형의 두 변 방향은 실제로 **서로 직교**한다. 그 두 방향의 소실점 `v₁`·`v₂` 는 `H` 의 1·2 열이다
(평면의 무한 원점 `(1,0,0)`·`(0,1,0)` 의 상). 소실점으로 가는 광선 `K⁻¹v` 가 곧 그 방향이므로 `(K⁻¹v₁)·(K⁻¹v₂) = 0`.
정사각 화소·주점 `(cx,cy)` 인 `K = [[f,0,cx],[0,f,cy],[0,0,1]]` 을 넣어 `f²` 로 정리하면

```
(v₁x − cx)(v₂x − cx) + (v₁y − cy)(v₂y − cy) + f² = 0      →      f = √( −[ … ] )
```

`null` 로 떨어지는 경우:

- 소실점이 **무한대** — `|v − c|` 가 사진 대각선의 200배를 넘으면 변이 0.3° 안쪽으로 평행하다는 뜻이다. 그때 `f` 는
  잡음이 통째로 결정한다.
- 대괄호 안이 **음수가 아니다** — 정사각 화소 카메라가 직사각형을 찍어 만들 수 없는 네 점이다.
- 풀린 **가로 화각이 5°~150° 밖** — 실제 렌즈가 아니다.

### ③ 평면 자세 분해 — `plannerPhotoPose(H, f, cx, cy)`

`K⁻¹H = λ·[r₁ r₂ t]` (평면의 세 번째 축은 0 이라 3열 자리에 `t` 가 온다).

1. 배율: `λ = 1/√(|r₁|·|r₂|)` — 한쪽만 쓰면 잡음에 치우친다.
2. 부호: **평면이 카메라 앞**이어야 한다 (`t_z > 0`). `H` 와 `−H` 는 같은 사영이라 해가 둘이다.
   `r₁`·`r₂`·`t` 를 같이 뒤집으므로 `r₃` 는 그대로다.
3. 직교화: `r₁` 을 단위로 → `r₃ = r̂₁ × r₂` 를 단위로 → **다시** `r₂ = r₃ × r₁`.
   이래야 `R` 이 정확히 회전행렬(직교·행렬식 +1)이 된다.

돌려주는 `R` 은 **모델 → 카메라**, 카메라 관례는 OpenCV (**X 오른쪽 · Y 아래 · Z 앞**).

### ④ 한 방에 — `plannerPhotoCamera(quad, rect, imgW, imgH, opt)`

모델 평면 (u,v) → 세계 mm 는 열이 `[Ex, Ez, En]` 인 회전행렬 `M` 이다
(`Ex = (cosθ,0,−sinθ)`, `Ez = (sinθ,0,cosθ)`, `En = Ex×Ez = (0,−1,0)`, `θ = −rotationDeg`).
그러면 `X_cam = R·(Mᵀ(X_world − O)) + t` 이고,

- **위치** = `M·(−Rᵀt) + O`
- `Rw = R·Mᵀ` 의 행이 카메라 축(세계 좌표). 0행 오른쪽 · 1행 **아래** · 2행 앞.
- **시선** = `Rw` 2행, **up(three)** = `Rw` 1행을 뒤집은 것
- **타깃** = 위치 + 시선 × `t_z`. 사각형 중심이 아니다 — 중심이 화면 한가운데 있으리라는 보장이 없고,
  `lookAt(target)` 이 이 자세를 **그대로** 만들어야 한다.

## 좌표계 — 헷갈리는 세 가지

| 이름 | 단위 | 원점·방향 | 어디에 |
|---|---|---|---|
| 사진 정규 좌표 | 0~1 | 좌상단 (0,0), y 아래 | `quad` 입력. 사진을 줄여도 안 깨진다 (계획 §4.4 `quad jsonb`) |
| 사진 픽셀 | px | 좌상단 (0,0), y 아래 | `imgW`·`imgH` 를 곱한 것. `f`·`reprojectionPx` 의 단위 |
| 플래너 세계 | **mm** | Y-up, 바닥 `y = 0`, 배율 없음 | `rect`·`position`·`target` (`mockup-structure.html:5887-5902`) |
| 카메라 (내부) | mm | OpenCV — X 오른쪽 · **Y 아래** · Z 앞 | `plannerPhotoPose` 의 `R`·`t` 만 |

마지막에 y·z 의 부호를 뒤집어 three 관례(Y 위 · **−Z 앞**)로 넘긴다.

### 바닥 사각형의 귀퉁이 순서 (정본)

`plannerPhotoRectCorners(rect)` 가 정한다. **0 뒤-왼 · 1 뒤-오른 · 2 앞-오른 · 3 앞-왼.**
"뒤" 는 평면도 위쪽(벽 쪽, 지역 −Z), "앞" 은 아래쪽(보는 사람 쪽, 지역 +Z).
보통 사진에서는 뒤 두 점이 위에 오므로 **사진 좌표(y 아래)로 시계 방향**이다.

`rect` 는 `{ w, d, originMm:{x,z}, rotationDeg }` — 배치 공간의 `W`·`D`(맞바꾸기 전 원값. 90/270 은 회전이 대신한다),
바닥 중심의 세계 좌표(원점 오프셋을 이미 뺀 값), 평면도 회전각. 3D 는 `rotation.y = −rotationDeg` 로 돈다
(`mockup-structure.html:7243-7266`, `planeBoxOf` `:1741-1749`).

**실제 치수는 사람이 넣지 않는다** — 배치 공간에서 자동으로 온다 (2026-09-17 결정, 계획 §9-2).

### 화각 — 가로와 세로

three 의 `PerspectiveCamera(fov, …)` 는 **세로** 화각이다 (`planner-capture.js:469`).
반면 이 풀이가 자연스럽게 내는 것 — 그리고 사람이 "화각 60도" 라고 말할 때의 것 — 은 **가로** 화각이다.

| 필드 | 뜻 |
|---|---|
| `fov` | **세로** 화각(도). three 에 그대로 넣는 값. `2·atan(imgH / 2f)` |
| `fovDeg` | **가로** 화각(도). 슬라이더·`opt.assumedFovDeg`·`opt.fovDeg` 가 말하는 값. `2·atan(imgW / 2f)` |

`aspect` 는 `plannerCaptureClampAspect` (0.5~3, `planner-capture.js:206`) 로 **자르지 않는다**.
사진 종횡비를 자르면 원근이 어긋나 합성이 통째로 틀어진다. 보통 사진은 어차피 그 범위 안이다
(4:3 = 1.33 · 16:9 = 1.78 · 9:16 = 0.56).

## 돌려주는 모양

`plannerCaptureFrame` 과 **같은 모양**이라 `PlannerCapture.capturePixels` 의 카메라 조립(`:469-474`)과
저장 배관이 통째로 재사용된다.

```js
{ kind:'photo', fov, aspect, position[3], target[3], up[3], near, far, dist,   // ← plannerCaptureFrame 과 같다
  f, fovDeg, method:'vanishing'|'assumed', reprojectionPx, reprojectionMaxPx, flipped, quadOrder }
```

- `near` 는 캡처 기본값과 같은 10, `far` 는 `ceil(dist·4 + 사각형대각 + 20000)`. `opt.near`/`opt.far` 로 덮을 수 있다.
- `reprojectionPx` 는 네 귀퉁이 재투영 오차의 **RMS**, `reprojectionMaxPx` 는 그중 최대. 항상 화면에 보여 준다 (계획 §4.2).
- `flipped` 는 사용자가 사각형을 반대로 돌려 찍었다는 표시다. **거절하지 않는다** — 첫 점은 그대로 두고 나머지를
  거꾸로 돌려(`quadOrder = [0,3,2,1]`) 받아들인다. 같은 카메라가 나온다.
- 나쁜 입력·퇴화로 못 풀면 **`null`**. 절대 던지지 않는다.

## 퇴화 — 숨기지 않는다

정면에서 찍은 사진은 사각형의 한 쌍의 변이 사진에서도 평행하다. 그 소실점이 무한대라 **초점거리가 정해지지 않는다.**
이때 `method:'assumed'` 로 떨어지고 기본 **가로 화각 60°** 를 쓴다 (`opt.assumedFovDeg` 로 바꾼다).
P1 의 UI 는 그때 화각 슬라이더를 **열어야** 한다 (계획 §8).

측정해 보니 쓸 만한 성질이 하나 있다 — **틀린 화각은 재투영 오차로 드러난다.**
자세 분해의 직교화 단계가 `f` 를 검산해 주기 때문이다. 3600×700 바닥을 정면에서 찍은 사진에서:

| 진짜 가로 화각 | 가정 화각 | 재투영 RMS | 위치 오차 | 푼 카메라 높이 (진짜 1700mm) |
|---|---|---|---|---|
| 45° | 60° | 158.8 px | 1413 mm | 1944 mm |
| 60° | 60° | **0.0 px** | **0 mm** | 1700 mm |
| 75° | 60° | 133.2 px | 930 mm | 1536 mm |

→ P1 의 화각 슬라이더는 **재투영 오차를 줄이는 방향**으로 돌리면 된다.

## 사각형 검사 — `plannerPhotoQuadSane(quad)`

`{ ok, reason, area, winding }`. `winding` 은 사진 좌표에서 시계 방향이면 `1`, 반시계면 `−1` (둘 다 통과).

| 거절 이유 (한국어 그대로) | 언제 |
|---|---|
| `네 점이 필요합니다` | 배열이 아니거나 개수가 다르다 |
| `좌표에 숫자가 아닌 값이 있습니다` | NaN·문자열 등 |
| `좌표가 사진 밖입니다 (0~1 이어야 합니다)` | 정규 좌표를 벗어났다 |
| `같은 점이 두 번 찍혔습니다` | 두 점 사이가 1e-4 미만 |
| `세 점이 한 직선 위에 있습니다` | 이웃 변의 외적이 0 — 넓이 0 포함 |
| `사각형이 꼬였습니다 (변끼리 교차합니다)` | 마주 보는 변이 실제로 교차 (나비넥타이) |
| `사각형이 오목합니다 (귀퉁이 하나가 안으로 들어갔습니다)` | 볼록하지 않은데 꼬이지는 않았다 |
| `사각형이 너무 작습니다` | 사진 넓이의 0.2% 미만 (4032×3024 에서 약 24,000 px²) |

오목/꼬임은 **마주 보는 변의 교차**로 가른다. 대각선 교차로는 못 가른다 — 둘 다 교차하지 않는다.

## 측정한 정확도

`__tests__/photo-solve.test.js` 가 실제로 돌려 나온 값이다 (2026-09-17). 시험은 **자기 전방 투영을 따로 갖고 있다** —
모듈의 재투영을 양방향에 쓰면 순환이라 증명이 되지 않는다.

### 정확한 입력 — 3576가지 배치

화각 20/35/50/65/80° × 높이 1200/1700/2500mm × 방위각 6가지(−55°~55°) × 거리 2가지 × 롤 0·5° ×
사각형 5가지(600×600 ~ 4200×700, 2400×1500) × 배치 회전 0·30°.

| 값 | 최대 오차 |
|---|---|
| 카메라 위치 | **2.8 × 10⁻⁸ mm** |
| 시선 방향 | **1.7 × 10⁻⁶ °** |
| up 방향 (롤) | 1.9 × 10⁻⁶ ° |
| 세로 화각 | 3.0 × 10⁻¹¹ ° |
| 재투영 RMS | 8.9 × 10⁻¹⁰ px |

전부 `method:'vanishing'` — 비스듬히 본 배치에서 가정 화각으로 떨어진 경우는 **0건**이다.
건너뛴 24가지는 사각형이 프레임 밖으로 나가거나 손으로 찍기엔 너무 납작한 배치다.

즉 **수학 자체는 기계 정밀도**다. 실제 오차는 전부 사람이 점을 어디에 찍느냐에서 온다.

## 이 수학이 못 하는 것 (솔직하게)

1. **주점을 사진 한가운데로 가정한다.** 잘라낸(crop) 사진이나 틸트-시프트 렌즈는 어긋난다. 네 점으로는
   주점까지 풀 수 없다 — 미지수가 모자란다.
2. **렌즈 왜곡을 보정하지 않는다.** 휴대폰 광각은 가장자리에서 직선이 휜다. 사각형을 화면 가장자리에 걸치지
   않게 잡으라고 안내하는 것 말고는 방법이 없다 (계획 §8).
3. **정면 사진에서는 화각을 못 구한다.** 원리적 한계다. `method:'assumed'` + 슬라이더가 유일한 답이다.
4. **첫 점이 어느 귀퉁이인지는 검사하지 못한다 — 그리고 180° 어긋남은 오차로도 안 잡힌다.**
   감기(시계/반시계)는 정규화하지만 **시작 귀퉁이**는 사용자가 맞춰 줘야 한다. 3600×700 · 2400×1500 등에서
   측정한 결과 (진짜 카메라 `(−959, 1700, 3893)`):

   | 시작 귀퉁이가 어긋난 칸 수 | 푼 위치 | 위치 오차 | 재투영 RMS |
   |---|---|---|---|
   | 0 (맞음) | (−959, 1700, 3893) | 0 mm | 0.0 px |
   | 1 · 3 (90°) | (4393, 1700, 2459) | 5540 mm | **443.5 px** ← 잡힌다 |
   | 2 (180°) | (2959, 1700, −2893) | **7835 mm** | **0.0 px** ← 안 잡힌다 |

   직사각형은 180° 회전에 대해 자기 자신이라 대각선 반대 귀퉁이에서 시작하면 **재투영 오차가 정확히 0 인,
   방 반대편에서 본 카메라**가 나온다. 정사각형(600×600)이면 90° 어긋남도 마찬가지로 안 잡힌다.
   → **P1 의 UI 는 귀퉁이에 이름표("벽 쪽 왼편"…)를 붙이고 찍는 순서를 강제해야 한다.** 숫자로는 못 막는다.
5. **네 점은 여유가 없다.** 최소해라 잡음을 걸러낼 수 없다. 점을 더 찍게 해서 최소제곱으로 푸는 것은
   이 PR 의 범위 밖이다 — 필요해지면 `plannerPhotoHomography` 를 8×8 에서 최소제곱으로 넓히면 된다.
