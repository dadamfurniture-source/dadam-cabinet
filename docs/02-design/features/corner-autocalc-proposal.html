멍장(코너장) 자동계산 구조 설계안

ㄱ자 배치에서 멍장과 secondary 라인을 데이터 모델의 1급 시민으로 승격시키고, 모든 치수를 하나의 순수 함수에서 파생시키는 설계. 자동계산·3D·BOM이 같은 숫자를 보게 만드는 것이 핵심이다.

01설계 철학 — 파생(derive), 저장(store)하지 않는다

현재 구조의 문제는 코드가 아니라 데이터의 소유권에 있다.

지금 멍장의 치수는 두 곳에서 서로 다른 공식으로 만들어진다. 데이터 모델(ui-workspace.js)은 W=secondaryD로 저장하고, 3D 미리보기(ui-step1.js)는 W=primeD+40으로 즉석 생성한다. 둘은 동기화 코드가 없으므로 필연적으로 어긋난다.

제 설계의 첫 번째 원칙은 이것입니다: 멍장의 치수는 어디에도 "입력"되지 않는다. 벽 스펙(primeD, secondaryD, 높이)이 바뀔 때마다 단 하나의 순수 함수 deriveCorner()가 재계산한다. 제안

02기하학 — 코너는 누구의 것인가

ㄱ자의 모든 치수 규칙은 "코너 사각형을 누가 점유하는가"에서 파생된다.

두 라인이 만나는 코너에는 primeD × secondaryD 사각형이 생기고, 이 공간에는 캐비닛이 하나만 들어갈 수 있다 — 그것이 멍장이다. 멍장을 secondary 라인의 첫 모듈로 정의하면(3D 코드·mcp-server의 blindAnchorIdx 방식과 일치) 치수가 다음처럼 정리된다. 제안

+40mm의 기하학적 의미: secondary 라인의 두 번째 모듈(첫 수납 모듈)의 도어가 열릴 때, prime 라인 캐비닛의 전면(도어면)과 간섭하지 않으려면 멍장이 prime 깊이보다 여유분만큼 더 뻗어야 한다. 사용자 확정 공식이 이 여유를 40mm로 정의한다. 확정

04데이터 모델 — 모듈에 line 좌표를 부여

orientation은 "어떻게 그릴까"(회전)이고, line은 "어느 벽 소속인가"(계산 단위)다. 지금은 orientation 하나가 두 역할을 겸하고 있다.

// item.modules 안의 멍장 — deriveCorner()가 생성/갱신
{
  id: 'corner-blind-lower',       // 고정 id: 재생성 시 중복 방지
  name: 'LT망장',
  type: 'storage',
  pos: 'lower',
  line: 'secondary',              // ★ 신규: 계산 소속 라인
  orientation: 'secondary',       // 기존: 3D 회전 표현 (유지)
  w: 590, h: 730, d: 550,           // deriveCorner() 파생값 — 직접 수정 금지
  isFixed: true,                  // 분배 대상 제외 (보호는 isFixed가 담당)
  isDerived: true,                // ★ 신규: specs 변경 시 자동 재계산 표식
}

// secondary 수납 모듈 — 사용자가 편집 가능, 자동계산이 분배
{
  id: 1752671623001,
  name: '2단 서랍장', type: 'storage', pos: 'lower',
  line: 'secondary', orientation: 'secondary',
  w: 605, h: 730, d: 550,
}
  • line 필드 추가 제안 — 자동계산이 !m.orientation 같은 부정 필터 대신 m.line === 'prime'으로 명시 선택한다. 기존 모듈은 line 부재 시 'prime'으로 간주 → 하위 호환.
  • isDerived 플래그 제안 — 멍장처럼 공식에서 파생되는 모듈의 표식. specs 변경 이벤트에서 이 플래그가 있는 모듈만 골라 재계산한다. 사용자 임의 치수 수정과의 충돌을 UI에서 차단하는 근거도 된다.
  • 고정 id — Date.now()+random 대신 corner-blind-lower처럼 결정적 id를 부여해 ㄱ자↔ㅡ자 전환 반복 시 멍장이 중복 생성되는 사고를 막는다. calc-engine.js:919의 hasSecondaryLT 가드도 id 기반으로 단순화.

05자동계산 알고리즘 — 라인은 "작은 ㅡ자"다

새 분배 알고리즘을 만들지 않는다. 검증된 prime 분배 로직을 라인마다 재사용한다.

핵심 통찰: secondary 라인은 예산이 1210mm인 작은 ㅡ자 주방일 뿐이다. 기존 calc-engine의 분배·갭 흡수·최소폭 규칙이 이미 ㅡ자에서 검증되어 있으므로, 그 함수를 라인 단위로 호출하도록 감싸기만 하면 된다. prime 경로 코드는 한 줄도 바뀌지 않는다 — 회귀 위험 최소화의 핵심.

function runAutoCalcLower(item) {
  // ① 파생 치수 갱신 — 멍장 W/H/D, 라인 예산
  const corner = deriveCorner(item.specs);        // { blind, budgets }
  syncDerivedModules(item, corner);                // isDerived 모듈만 갱신

  // ② 라인 분리 — 명시적 소속 기준
  const prime = item.modules.filter(m => m.pos==='lower' && lineOf(m)==='prime');
  const sec   = item.modules.filter(m => m.pos==='lower' && lineOf(m)==='secondary' && !m.isFixed);

  // ③ 동일 엔진, 라인별 예산 — 기존 분배 함수 그대로 재사용
  distributeModules(prime, corner.budgets.prime);   // 기존 로직 무변경
  distributeModules(sec,   corner.budgets.secondary);

  // ④ 갭 흡수 — 라인 안에서만 (라인 간 이동 금지)
  absorbGap(prime, corner.budgets.prime);           // 개수대 확장 우선 규칙 유지
  absorbGap(sec,   corner.budgets.secondary);

  // ⑤ 불변식 검증 + 병합 (배치 순서: 멍장 → sec → prime, startSide 반영)
  assertLineWidths(item, corner);
  item.modules = mergeInPlacementOrder(corner.blind, sec, prime, item.specs.startSide);
}

단계별 근거

  • ① 이 갱신이 맨 앞인 이유 — 사용자가 primeD를 550→600으로 바꾸면 멍장 W가 590→640으로 변해야 하고, 그 변화가 secondary 예산(−50)에 즉시 반영된 뒤 분배가 돌아야 한다. 순서가 뒤집히면 한 사이클 지연된 값으로 계산된다.
  • ④ 라인 간 이동 금지 — 갭은 발생한 라인 안에서 흡수한다. prime의 부족분을 secondary 모듈을 줄여 메우는 식의 교차 보정은 사용자가 예측할 수 없는 결과를 만든다. 라인은 독립된 계산 단위다.
  • 가전(냉장고 등)이 secondary에 있는 경우 — 기존 엔진의 고정폭 처리(isFixed)가 라인 안에서 그대로 동작한다. 별도 코드가 필요 없다는 것이 재사용 설계의 이점.
ㄷ자(U형) 확장은 공짜로 따라온다 이 구조에서 tertiary는 line:'tertiary' + 예산 하나가 추가될 뿐이다. W11에서 ㄷ자를 다룰 때 알고리즘 변경이 아니라 deriveCorner()에 코너 2번째 항목을 추가하는 일이 된다.

07멍장 내부 구조 — 규칙 확정 대기 규칙 필요

구조(파이프라인)는 지금 만들고, 부재 산식은 규칙이 오면 꽂는다.

내부 부재 규칙은 제작 현장의 것이라 제가 임의로 정하지 않는다. 대신 부재 산출을 전략(strategy)으로 분리해서, 규칙이 확정되는 즉시 교체 가능한 구조를 제안한다:

// extractors.js — 멍장 부재 전략 분리
const BLIND_PART_STRATEGY = {
  standard: extractStandardCarcass,   // A안: 현행 일반 카카스 산식 재사용
  blindSpecific: extractBlindCarcass, // C안: 규칙 확정 후 구현
};
A안 · 1차 배포 기본값

표준 카카스 재사용

측판 2 · 천판/지판 · 뒷판 · 선반 · 도어를 기존 extractSink 산식으로. BOM이 즉시 나온다. 부재 수량은 정확하고, 코너 특화 형상만 미반영.

B안 · 현행 데이터 유지

서랍 고정 모듈

현재 isDrawer: true 정의 유지. 서랍 레일·서랍장 부재 산식 적용. 실제 제작이 서랍형이라면 이쪽이 정답.

C안 · 규칙 확정 후

블라인드 특화 부재

데드존 격벽, 반폭 도어(W − 데드존), 축소 선반 등 코너 전용 산식. 제작 도면을 받아 corner.md에 규칙을 먼저 문서화한다.

진행 방식: A안으로 파이프라인 전체(영속화→자동계산→BOM)를 먼저 관통시켜 배포하고, 내부 규칙이 확정되면 전략 함수 하나만 C안으로 교체한다. 규칙 대기가 전체 일정을 막지 않게 하는 구조다.

기존 저장 설계 호환 (FR-07)

persistence-init.js 로드 시점에 1회 보정을 실행한다:

  1. layout이 L인데 line:'secondary' 수납 모듈이 0개면 → deriveCorner() + 기본 분배로 생성
  2. 구식 멍장(W=secondaryD로 저장된 것)이 있으면 → isDerived 부여 후 공식값으로 재계산
  3. line 필드가 없는 모듈은 → orientation 값으로 역추론 (orientation 없음 = prime)

보정은 멱등(idempotent)하게 — 같은 설계를 두 번 열어도 결과가 같아야 한다. 고정 id(corner-blind-lower)가 이를 보장한다.

09왜 이 설계인가 — 대안과의 비교

설계 대안장점기각 사유
현행 유지 + 3D 로직만 BOM에 복제 변경 범위 최소 공식이 3곳으로 늘어난다. 지금의 2곳 불일치가 이미 사고 원인 — 복제는 부채의 이자만 키움
코너를 별도 최상위 엔티티로 분리
(item.corner = {...})		 모델이 개념적으로 깔끔 extractors·정면도·persistence 등 item.modules 순회 코드 전부가 두 소스를 봐야 함. 16,500줄 코드베이스에서 수정 표면적이 과도
선택안: modules 배열 유지 + line/isDerived 필드 + deriveCorner() 기존 순회 코드 전부 호환 · 공식 단일화 · prime 로직 무변경 — (분배 함수의 라인 단위 재사용이 전제조건)

검증 계획

  • 단위: deriveCorner() 순수 함수 — 치수 공식·예산·엣지(secondaryW < blindW인 극단 케이스) 테이블 테스트
  • 불변식: 자동계산 후 라인 합계 assert (§03) — 개발 중에는 throw, 프로덕션에서는 콘솔 경고+보정
  • 회귀: ㅡ자 설계 자동계산 스냅샷 전/후 diff = 0 (prime 경로 무변경 증명)
  • E2E: ㄱ자 설정 → 자동계산 → 정면도(W9 ruler) → BOM 수량이 §06 검산표와 일치
  • 호환: 기존 저장 ㄱ자 설계 로드 → 보정 → 재저장 → 재로드 멱등성
