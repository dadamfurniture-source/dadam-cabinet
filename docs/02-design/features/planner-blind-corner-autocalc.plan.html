설계 계획 · 플래너 W12-48

ㄱ자 코너에 멍장을 세우는 자동계산

배치 단계에서 그린 ㄱ자가 구조 단계로 넘어오면, 두 다리가 코너에서 같은 자리를 주장한다. 멍장은 그 자리를 쓸 수 있는 수납으로 바꾸는 유일한 부재다. 규칙은 이미 확정돼 있고 레거시 경로에서 검증까지 끝났다 — 플래너로 옮기면서 새로 정해야 하는 것만 여기 적는다.

대상 mockup-structure.html · planner-engine.js 근거 규칙 docs/design-rules/corner.md §3~§4 선행 구현 corner-engine.js (W10-1~W10-5, PR #423~428)

01한 장 요약

무엇을 고치는가 — 세 문장.

  1. 지금 autoCalcArea 는 배치 공간 하나만 보고 그 폭을 전부 도어로 나눈다. 코너라는 개념이 코드에 없다. 그래서 ㄱ자의 두 다리가 코너 사각형을 각자 채워 모듈이 겹친다.
  2. 바꿀 것 자동계산 전에 코너를 기하에서 찾아내고, 멍장을 isFixed 모듈로 먼저 심는다. 그 뒤는 기존 분배 로직이 그대로 돈다 — 고정 모듈을 보존하고 나머지만 나누는 길이 이미 있다 (§9.16 마감재 균등 분배와 같은 자리).
  3. 안 바꿀 것 멍 공식·도어 균등 분배·원장 불변식은 corner.md §3 그대로다. 새 규칙을 만들지 않는다.

이 계획의 핵심 주장

멍장은 코너에 추가로 넣는 장이 아니라, 두 배치 공간이 겹치는 사각형의 소유권을 한쪽에 넘기는 규칙이다. 그렇게 보면 "겹침 해소"와 "코너 활용"이 같은 한 번의 계산으로 풀린다.

02지금 코너에서 벌어지는 일

배치 단계가 넘겨주는 ㄱ자는 두 가지 상태 중 하나다. 둘 다 멍장을 세울 수 없다.

trimAgainst 는 자른 쪽 사각형이 기준 사각형의 면에 정확히 맞닿게 만든다 (mockup-shell.html, 여유 0). 물끊기 10 도 코너 몰딩 60 도 들어갈 틈이 없다. 즉 트리밍은 코너를 "정리"하는 것처럼 보이지만, 규칙이 요구하는 50mm 상당의 여유를 함께 지운다.

그래서 구조 단계는 배치 좌표를 그대로 믿으면 안 된다

트리밍 여부에 따라 같은 ㄱ자가 다른 답을 내면 안 된다. 구조 단계는 두 영역의 벽선(뒤판선)에서 코너 사각형을 다시 세워 계산한다 — A 든 B 든 같은 값이 나온다. 배치 좌표는 건드리지 않는다.

2026-07-17 확정, 레거시 경로에서 프로덕션 검증까지 끝난 규칙이다.

플래너가 이 코드를 그대로 못 쓰는 이유

corner-engine.js 도 data-constants.js 도 detaildesign.html 만 로드한다. 플래너 두 페이지는 js/planner/*.js 넷만 싣는다. 그리고 입력이 다르다 — 레거시는 item.specs 의 선언된 라인(layoutShape:'L', secondaryW)을 읽고, 플래너에는 그런 선언이 없다. 사각형만 있다.

04코너를 기하에서 찾는다

플래너에는 prime·secondary 라는 선언이 없다. 회전과 좌표만 있다.

배치 공간은 { id, section, W, H, D, x, y, rotation } 이 전부다. W12-36 이 planeBoxOf(area) 를 정본으로 만들어 두었으므로, 평면에서 차지하는 자리는 회전을 포함해 이미 정확히 구할 수 있다. 코너 판정은 그 위에 얹는다.

function cornerPairs(areas) {
  // 실제 배치 공간만 — 마감재 영역·스택 영역은 코너를 만들지 않는다
  const live = areas.filter(a => !a.isFinishing && !isStackedArea(a));
  const out = [];
  for (const [a, b] of pairsOf(live)) {
    // (1) 서로 직각이다 — 회전 차가 90도 (mod 180)
    if ((rotOf(a) - rotOf(b) + 360) % 180 !== 90) continue;
    // (2) 같은 단이다 — 하부장 다리와 상부장 다리는 코너를 공유하지 않는다
    if (tierOf(a) !== tierOf(b)) continue;
    // (3) 평면에서 만난다 — 겹치거나(트리밍 전) 맞닿아 있다(트리밍 후)
    const sq = cornerSquare(planeBoxOf(a), planeBoxOf(b));
    if (!sq || sq.gap > CORNER_TOUCH_TOL) continue;
    out.push({ a, b, square: sq });
  }
  return out;
}

코너 사각형은 두 다리의 깊이가 만드는 영역이다 — 세로 다리의 깊이(X 폭) × 가로 다리의 깊이(Y 폭). 트리밍으로 실제 사각형이 잘려 있어도 두 영역의 벽선에서 되세우면 같은 값이 나온다. 이것이 §02 에서 말한 "배치 좌표를 그대로 믿지 않는다" 의 구현이다.

판정기준왜
직각회전 차 90도 (mod 180)같은 회전은 한 줄로 이어진 배치다 — 코너가 아니다
같은 단lower↔lower, upper↔upper하부 코너와 상부 코너는 멍 공식이 다르다 (§3.3 vs §3.6)
접촉평면 간극 ≤ CORNER_TOUCH_TOL겹침(트리밍 전)과 맞닿음(트리밍 후)을 한 조건으로 받는다
스택 제외isStackedArea키큰장·냉장고장은 단이 겹쳐 서므로 도어 균등 분배 대상이 아니다

정해야 할 것 — CORNER_TOUCH_TOL 의 값

사람이 손으로 그린 사각형은 몇 mm 어긋난다. 너무 빡빡하면 코너를 못 찾고, 너무 헐거우면 코너가 아닌 것을 코너로 본다. 제안: 20mm — 배치 단계 스냅 단위보다 크고, 가장 얇은 부재(EP 20)보다 크지 않다.

05멍장의 주인 정하기

코너를 이루는 두 영역 중 어느 쪽이 멍장을 갖는가. 규칙은 "사용자 결정"이라고만 한다.

corner.md §3.2 는 멍장이 prime 이든 secondary 든 갈 수 있다고 하고, 레거시는 secondary 하나만 구현했다 (prime 은 준비중으로 남았다). 플래너에는 그 이름이 없으니 기하로 대응시켜야 한다.

제안 — 회전한 다리가 주인

rotation !== 0 인 영역이 멍장을 갖는다. 배치 단계에서 주벽면은 회전 0 으로 그리고 꺾여 나가는 다리에 회전을 준다 — 레거시의 prime / secondary 와 그대로 대응한다.

둘 다 회전이 0 이 아니면 x + y 가 큰 쪽(원점에서 먼 쪽)을 주인으로 한다. 결정적이고, 재계산해도 흔들리지 않는다.

버린 안 — 짧은 다리가 주인

"짧은 쪽에 멍장" 은 현장 관행처럼 들리지만, 두 다리 길이가 비슷하면 몇 mm 차이로 주인이 바뀐다. 배치를 조금만 고쳐도 코너 전체가 재배치된다 — 자동계산이 사람 손을 뒤엎는 가장 나쁜 방식이다.

기본값은 자동으로 정하되 영역 도구에 토글을 둔다 — [멍장: 이 영역 / 상대 영역]. 사람이 정한 값은 area.blindOwner 로 남고 자동 판정보다 우선한다.

06계산 — deriveCornerArea()

순수 함수 하나. 상태를 읽지 않고 두 영역과 상수만 받는다.

function deriveCornerArea({ owner, adj, molding = 60, epW = 20, isUpper = false }) {
  // (1) 멍 — §3.3 / §3.6
  const blindZoneW = isUpper
    ? CORNER_UPPER_MODULE + molding                 // 320 + 60 = 380
    : topDepthOf(adj) - CORNER_DRIP + molding;      // 650 - 10 + 60 = 700

  // (2) 도어 균등 분배 — 라인 전체가 한 번에 나뉜다 (§3.4)
  const doorAvail = owner.W - epW - CORNER_WALL_GAP - blindZoneW;   // 1200
  const nDoors   = Math.max(1, Math.floor(doorAvail / DOOR_W_MIN)); // 3
  const doorW    = Math.floor(doorAvail / nDoors);                 // 400

  // (3) 멍장 W = 멍 + 도어 1장
  const blindW = blindZoneW + doorW;                               // 1100

  // (4) 인접 다리는 멍장쪽 깊이만큼 밀려 시작한다 (§3.7)
  const adjStartOffset = isUpper
    ? CORNER_UPPER_MODULE + molding
    : topDepthOf(owner) - CORNER_DRIP + molding;                     // 700

  return { blindZoneW, doorW, nDoors, blindW, adjStartOffset, warnings };
}

남은 도어 예산 doorAvail − doorW = 800 은 도어 우선으로 나눈다 — 모듈 W 는 항상 도어 수 × doorW 다. 라인 전체의 도어가 같은 폭이어야 한다는 §3.4 를 지키려면, 일반 distributeModules 를 그대로 쓸 수 없다. 멍장이 있는 영역만 distributeByDoorW(budget, doorW) 로 간다.

정해야 할 것 — topDepthOf(area) 가 무엇인가

규칙은 상판 깊이를 쓴다. 플래너의 area.D 는 W12-25 이후 몸통 + 도어다 — 상판은 보통 그보다 앞으로 더 나온다. 둘을 같다고 보면 멍이 상판 돌출만큼 짧아진다.

제안: 우선 area.D 를 상판 깊이로 본다. 레거시가 primeTopD 에 사실상 같은 값을 넘기고 있고 프로덕션 검증도 그 값으로 통과했다. 상판 돌출을 따로 모델링하는 것은 별도 항목으로 남긴다 (§13).

07원장 불변식 — 계산이 맞았는지 스스로 검사한다

멍장 계산은 조용히 틀린다. 화면에는 멀쩡한 장이 서 있고 합만 안 맞는다.

멍장 영역   EP + Σ(모듈 W) + 멍장 W + 50  ===  area.W   (±1)
인접 영역   adjStartOffset + Σ(모듈 W)  ===  area.W   (±1)
평면        멍장 박스 ∩ 인접 영역 모듈 박스  ===  공집합

앞의 둘은 레거시 assertCornerLedger 와 같은 식이다. 셋째는 플래너에만 필요하다 — 레거시는 라인이 선언돼 있어 겹칠 수가 없지만, 플래너는 좌표로 놓으므로 실제로 겹쳤는지를 봐야 한다. W12-25 의 파츠 불겹침 검사와 같은 도구를 쓴다.

위반 시 콘솔 경고 + 마지막 모듈 보정(운영), 테스트에서는 실패시킨다.

08자동계산에 끼워 넣는 자리

기존 코드를 고치는 것이 아니라, 이미 뚫려 있는 길로 들어간다.

autoCalcArea 는 이미 고정 모듈을 보존하고 나머지만 나눈다. 마감재 균등 분배(§9.16)가 이 길을 냈다. 멍장은 isFixed: true 이므로 그 길에 그대로 얹힌다 — 분배 루프를 고칠 필요가 없다.

코너가 없는 배치에서는 ensureCornerModules 가 즉시 반환하고 offset 이 0 이다. 골든 스냅샷 3건이 바이트 단위로 같아야 이 조건이 지켜진 것이다 — W12-36 이 회전 좌표를 고칠 때 쓴 것과 같은 판정이다.

멍장 모듈의 모양

{
  id: 'corner-blind-' + areaId,   // 결정적 id — 재계산해도 같은 모듈
  areaId, section: 'lower',
  W: 1100,                       // = 멍 700 + 도어 400 (파생값)
  H: area.H, D: area.D,
  isFixed: true,               // 자동계산이 지우거나 폭을 뺏지 않는다

이름은 LT망장 을 유지한다 — BOM 추출기가 그 이름으로 찾는다 (corner.md §3.8, 코드 호환용).

09실행 순서

멍장은 두 영역에 동시에 영향을 준다. 순서를 안 정하면 먼저 계산된 쪽이 이긴다.

지금 autoCalcAllAreas 는 areas 배열 순서대로 각 영역을 독립 계산한다. 멍장이 들어오면 그 독립성이 깨진다 — 인접 영역의 예산이 멍장 주인의 깊이에 달려 있다. 그래서 단계를 나눈다.

function autoCalcAllAreas() {
  // 1단계 — 코너를 먼저 확정한다 (모든 영역의 예산이 여기서 정해진다)
  const corners = cornerPairs(areas);
  corners.forEach(c => ensureCornerModules(ownerOf(c).id));

  // 2단계 — 각 영역을 채운다. 멍장은 isFixed 라 그대로 살아남는다
  targets.forEach(a => autoCalcArea(a.id));

  // 3단계 — 원장 검사 (§07)
  corners.forEach(assertCornerLedger);

  // 그리기는 여전히 한 번만 (W12-46)
}

영역 하나만 다시 계산할 때(이 영역 자동계산)도 같다 — 그 영역이 코너에 물려 있으면 1단계를 그 코너에 대해서만 먼저 돌린다. 멍장은 항상 분배보다 먼저 선다.

10막아야 할 경우들

멍장은 폭을 크게 먹는다. 들어갈 자리가 없을 때 반쯤 세우는 것이 가장 나쁘다.

상황조건처리
라인이 멍보다 짧다 W − EP − 50 < 멍 거부 멍장을 세우지 않는다. 필요한 최소 폭을 토스트로 알린다 (레거시 G1 과 같은 판단 — 거기서는 ㄱ자 전환 자체를 막았다)
도어 한 장도 안 남는다 0 < doorAvail < 350 경고 후 진행 nDoors=1, doorW=doorAvail. 멍장에 좁은 도어 한 장이 달린다 — 배지로 표시
사람이 멍장 폭을 고쳤다 isDerived 해제됨 파생을 멈추고 그 폭을 지킨다. 원장이 안 맞으면 경고만 — 사람 손을 덮지 않는다
코너에 마감재가 붙어 있다 EP·몰딩이 코너 쪽 끝 코너 쪽 끝은 멍장 자리다. 마감재는 반대쪽 끝으로만 — 붙이려 하면 막고 안내
한 영역이 두 코너의 주인 ㄷ자 가운데 다리 양끝에서 각각 멍장을 빼고 남은 폭을 나눈다 (§11)
세 영역이 한 점에서 만난다 비정상 배치 거부 코너 쌍을 못 정한다. 배치 단계에서 고치도록 안내

거부는 조용하면 안 된다

멍장을 못 세우면 코너는 지금과 똑같이 겹친 상태로 남는다. 그냥 넘어가면 사용자는 자동계산이 성공한 줄 안다. 거부할 때는 어떤 배치 공간이 몇 mm 모자란지 말해야 한다.

11상부장 · ㄷ자 · 스택

상부장

공식만 다르고 흐름은 같다 — 물끊기가 없고 멍이 320 + 몰딩 이다 (§3.6). 하부·상부 코너는 서로 독립이다. 상부 다리가 하부 다리와 길이가 달라도 상관없다.

상부   1800 = EP 20 + 도어 450×2 + 멍장 830 + 여유 50
             멍장 830 = 멍 380 + 도어 450

확인 필요 상부장 배치 공간의 기본 깊이도 320 이다 (area-upper-0.D = 320). CORNER_UPPER_MODULE 320 과 값이 같은 것은 우연인지 같은 뿌리인지 확인해야 한다 — 우연이라면 깊이를 바꾼 순간 멍이 조용히 틀린다.

ㄷ자

코너 2개. cornerPairs 가 쌍을 두 개 돌려주고 각각 독립으로 처리된다. 가운데 다리가 양끝 모두 코너일 수 있고, 그때 원장이 달라진다 — EP 가 없고 코너 여유가 둘이다.

가운데 다리   50 + 멍장A + Σ(모듈) + 멍장B + 50  ===  area.W

양끝에서 멍장 둘을 빼면 남는 폭이 급격히 준다. §10 의 "라인이 멍보다 짧다" 가 ㄷ자에서 훨씬 자주 걸린다 — 거부 안내가 실제로 중요해지는 것은 여기서다.

스택 영역 (키큰장 · 냉장고장)

코너 대상이 아니다. 단이 세로로 겹쳐 서므로 도어 균등 분배라는 개념이 없고 autoCalcStack 이 따로 돈다. cornerPairs 에서 제외한다.

확인 필요 키큰장이 코너에 놓이는 실제 시공이 있는지. 있다면 규칙이 없다 — §13 으로 넘긴다.

코너 상수는 지금 js/detaildesign/data-constants.js 에 있고, 플래너는 그 파일을 로드하지 않는다. MASTER_RULES 에 추가한다.

BOM

레거시 W10-4 가 이미 처리한 것을 그대로 따른다. 새로 만들지 않는다.

  • 도어는 doorW 기준 — 카카스 W(1100)로 발주하면 도어가 700mm 커진다. 이 사고가 실제로 있었고, 설계 문서의 경고에서 잡혔다
  • 멍 가림판 2.7T MDF — 멍 구간 정면을 막는다 (멍 W × 몸통 H)
  • 코너 몰딩 60 — 접합부

플래너 → BOM 경로(buildPlannerPayload)가 blind 필드를 실어 보내야 추출기가 도어 폭을 알 수 있다.
