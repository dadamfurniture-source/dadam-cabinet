도면 불러오기

배치 · 구조 · 디테일 세 단계의 저장 데이터를 계정에 귀속시키고, ⚡ 전체 자동계산 왼쪽의 드롭다운에서 단계별로 불러옵니다. 지금 이 데이터는 전부 브라우저 localStorage 에만 있습니다 — 캐시를 지우면 사라지고, 다른 PC 에서는 아예 보이지 않습니다. 그래서 이 작업은 UI 추가가 아니라 저장 위치를 옮기는 일입니다.

대상 mockup-structure.html · mockup-shell.html · database/ 선행 Supabase 마이그레이션 (직접 실행 필요) 막는 것 §06 결정 3건

01지금 어디에 저장되나

먼저 사실 확인. 플래너 두 페이지는 Supabase 를 아예 불러오지 않습니다.

mockup-structure.html · mockup-shell.html 이 로드하는 스크립트는 Three.js 와 js/planner/*.js 넷뿐입니다. supabase-js 도 js/config.js 도 없습니다. 저장은 전부 localStorage 입니다.

다만 키는 이미 품목 단위로 쪼개져 있습니다 — js/planner/planner-scope.js:

// 부모(detaildesign)가 iframe URL 로 ?design=&item= 을 넘긴다
PLANNER_SCOPE = `::${design}:${item}`

// js/detaildesign/ui-step1.js · _plannerScopeParams()
design = currentDesignId   // designs.id (UUID) — 저장 전이면 'local'
item   = item.uniqueId     // design_items.unique_id (BIGINT)

이게 좋은 소식입니다

스코프가 이미 (designs.id, design_items.unique_id) 입니다. DB 로 옮길 때 키를 새로 설계할 필요가 없습니다 — 지금 쓰는 두 값을 그대로 컬럼으로 세우면 됩니다.

02세 단계가 각각 무슨 데이터인가

단계만드는 곳저장 키 (localStorage)내용
배치mockup-shell.html dadam_layout_v1
dadam_origin_v1		 배치 공간 사각형 · 회전 · 사람 위치 · 원점/천정
구조mockup-structure.html dadam_struct_modules_v1
dadam_structure_v1		 모듈 목록(W·H·D·좌표·마감재·멍장) · 모듈별 구조(칸·도어·서랍·선반)
디테일detaildesign.html 이미 DB design_items specs JSONB · modules JSONB · 치수 · 고객 요청

디테일 단계는 이미 계정에 귀속되어 있습니다. design_items.design_id → designs.id → designs.user_id → auth.users 이고 RLS 도 걸려 있습니다 (database/rls-enhanced.sql). 그러니 이번 작업의 실질은 배치와 구조 둘을 같은 자리로 끌어오는 것입니다.

03저장 위치 — 새 표를 권합니다

두 가지 길이 있고, 갈림은 "한 품목에 도면을 여러 벌 두는가" 하나입니다.

안어떻게얻는 것잃는 것
A design_items 확장 layout JSONB · structure JSONB 컬럼 추가 표가 안 늘고, RLS 그대로 품목당 한 벌. 되돌리기·이력 없음
B planner_snapshots 새 표 권장 (design_id, item_unique_id, stage) 마다 행 여러 개 이름 붙여 저장 · 목록에서 골라 불러오기 · 되돌리기 표 하나 · RLS 정책 하나 추가

B 를 권하는 이유는 요청이 "저장"이 아니라 "불러오기" 이기 때문입니다. 불러올 것이 항상 한 벌이면 드롭다운이 필요 없습니다 — 페이지가 열릴 때 이미 그것을 씁니다. 드롭다운이 뜻을 가지려면 고를 것이 여럿이어야 합니다.

-- database/planner-snapshots-schema.sql (초안)
create table if not exists planner_snapshots (
  id              uuid primary key default gen_random_uuid(),
  design_id       uuid references designs(id) on delete cascade,
  item_unique_id  bigint,                      -- design_items.unique_id
  stage           text not null check (stage in ('layout','structure','detail')),
  name            text,                        -- 사람이 붙인 이름
  payload         jsonb not null default '{}', -- 아래 §04
  is_autosave     boolean default false,
  created_at      timestamptz default now(),
  updated_at      timestamptz default now()
);

create index on planner_snapshots (design_id, item_unique_id, stage, created_at desc);

alter table planner_snapshots enable row level security;

-- 소유권은 designs 를 타고 온다 — user_id 를 여기 두지 않는다.
-- 두면 designs 와 어긋날 수 있고, 어긋나면 남의 도면이 보인다.
create policy "own snapshots" on planner_snapshots
  for all
  using (exists (select 1 from designs d
                 where d.id = planner_snapshots.design_id
                   and d.user_id = auth.uid()))
  with check (exists (select 1 from designs d
                      where d.id = planner_snapshots.design_id
                        and d.user_id = auth.uid()));

이 SQL 은 제가 실행할 수 없습니다

Supabase 대시보드의 SQL Editor 에서 직접 돌리셔야 합니다. 파일은 저장소에 database/planner-snapshots-schema.sql 로 넣어 두겠습니다.

04payload 는 지금 키를 그대로 담습니다

변환하지 않습니다. 변환하면 그 변환이 새 버그 표면이 됩니다.

// stage = 'layout'
{ layout: <dadam_layout_v1 그대로>, origin: <dadam_origin_v1 그대로> }

// stage = 'structure'
{ modules: <dadam_struct_modules_v1>, structures: <dadam_structure_v1> }

// stage = 'detail' — design_items 가 정본. 스냅샷은 되돌리기용 사본만.
{ specs: …, modules: … }

불러오기는 localStorage 에 써 넣고 페이지의 기존 load 경로를 다시 타는 방식입니다. loadModules() · loadAreas() 가 이미 그 키를 읽고 있으니 새 파싱 경로를 만들지 않습니다.

05로그인은 어떻게 되는가

플래너는 detaildesign.html 안의 iframe 이고 같은 오리진입니다. Supabase 세션은 그 오리진의 localStorage 에 있으므로, 플래너 페이지가 supabase-js + js/config.js 를 로드하기만 하면 getSession() 이 부모의 로그인을 그대로 봅니다. 별도 로그인 화면이 필요 없습니다.

로그인이 없을 때

플래너를 단독 URL 로 열었거나 로그아웃 상태면 드롭다운은 "이 브라우저에 저장된 것" 만 보여주고, 목록 아래에 로그인하면 계정에 저장됩니다 를 답니다. 지금 동작이 그대로 남으므로 퇴행이 없습니다.

플래너에 스크립트 두 줄이 늘어납니다. 클래식 스크립트 전역 충돌 (planner-assets.test.js 가 지키는 그 문제) 을 피하려면 js/planner/*.js 앞에 두고, 이름은 window.supabase · window.DADAM_CONFIG 로 이미 격리돼 있어 안전합니다.

06결정이 필요한 것 막고 있음

Q1새 표(B)인가, 컬럼 추가(A)인가?

B 면 "이름 붙여 저장 → 목록에서 고르기"가 되고, A 면 품목당 한 벌만 자동 저장됩니다.

권장: B — 드롭다운이 뜻을 가지려면 고를 것이 여럿이어야 합니다.

Q2저장 시점은 자동인가, 버튼인가?

① 💾 구조 저장 을 누를 때만 · ② 바뀔 때마다 자동 + 수동 "이름 붙여 저장" 병행.

권장: ② — 자동은 is_autosave=true 로 한 행만 덮어쓰고, 수동 저장은 이름과 함께 행을 쌓습니다. 자동 저장이 이력을 더럽히지 않습니다.

Q3다른 품목·다른 설계의 도면도 불러올 수 있어야 하나?

지금 스코프는 (설계, 품목) 입니다. 드롭다운이 이 품목만 보여줄지, 내 모든 설계를 보여주고 골라 복사해 올지가 갈립니다.

권장: 1단계는 이 품목만. "다른 설계에서 가져오기"는 배치가 다른 벽 치수로 들어오면 트리밍·코너가 어긋나므로, 검증을 붙여 별도로 다뤄야 합니다.

07작업 순서

  1. 스키마 파일 + 직접 실행 database/planner-snapshots-schema.sql 을 넣고, Supabase SQL Editor 에서 실행하십시오. 이것이 끝나야 나머지가 의미를 갖습니다.
  2. 플래너에 Supabase 접속 두 HTML 에 supabase-js · js/config.js · js/supabase-utils.js 추가. 세션이 없으면 null 을 돌려주는 js/planner/planner-store.js 한 파일에 저장/불러오기를 모읍니다 — 두 페이지가 같은 정본을 쓰게.
  3. 저장 경로 연결 배치의 저장과 구조의 💾 구조 저장 이 localStorage 에 쓴 직후 같은 값을 스냅샷으로 올립니다. localStorage 쓰기는 그대로 둡니다 — 네트워크가 죽어도 작업이 멈추면 안 됩니다.
  4. 📥 도면 불러오기 드롭다운 ⚡ 전체 자동계산 왼쪽. 배치 / 구조 / 디테일 세 묶음, 각 묶음 아래 저장 시각과 이름. 고르면 localStorage 에 써 넣고 기존 load 경로를 다시 탑니다.
  5. 되돌릴 수 없는 지점에 확인 불러오기는 지금 작업을 덮어씁니다. 확인 대화 한 번 + "현재 상태를 자동 저장해 두었습니다" 안내를 붙입니다.
  6. 테스트 planner-store 순수 함수(스코프 → 키, payload 조립/해체) 단위 테스트와, 세션이 없을 때 localStorage 폴백이 도는지의 하네스 테스트.

08위험

불러오기는 파괴적입니다

지금 그린 배치를 지웁니다. 확인 없이 실행되면 한 시간 작업이 날아갑니다. §07-5 를 생략하지 마십시오.

design = 'local' 인 도면은 계정에 붙지 않습니다

설계를 저장하기 전에는 currentDesignId 가 없어 스코프가 ::local:bootstrap 입니다. design_id 가 null 이면 RLS 를 태울 소유자가 없으므로 DB 에 올리지 않고 localStorage 에만 둡니다. 설계를 저장하는 순간 local → 새 UUID 로 한 번 이관하는 경로가 필요합니다 (migrateLegacyScope() 와 같은 방식).
